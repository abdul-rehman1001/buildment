# 3.4 — Week 1 gate: publish and browse

> **[Gate]** · Module 03 — Events and ticket types · *Prove the organizer and buyer flow before you touch inventory*

## The demo

Week 1 ends with one honest demo:

1. An organizer signs up, verifies their email, and creates an organizer profile.
2. The organizer creates a draft event with a venue, time zone, start/end, and sale window.
3. The organizer adds two ticket types with prices, capacity, and per-order limits.
4. The organizer uploads a cover and publishes the event.
5. A buyer opens the public catalogue, searches for the event, and opens the page.
6. The page shows the correct local time, the cover, and both ticket types.
7. A draft or cancelled event does not appear in the catalogue or at a direct URL.

If any step requires a manual database edit, the flow is not finished. If the public page shows the server's time zone instead of the event's time zone, the flow is not finished. If a second organizer can edit the first organizer's event, the authorization model is not finished.

This gate is deliberately narrow. There are no holds, payments, tickets, or scans yet. The goal is to prove the foundation: identity, ownership, event lifecycle, time, capacity, storage, and search. Week 2 builds the hard concurrency and payment work on top of this foundation.

A good Week 1 review is not a tour of the screens. It is a set of claims backed by evidence. "The organizer can publish an event" is a claim; the evidence is a published event, a public page, and a second organizer who cannot edit it. "The time zone works" is a claim; the evidence is a winter date and a summer date displayed correctly. "The upload is safe" is a claim; the evidence is a presigned URL, a server-generated key, and a rejected client key.

A strong answer sounds like this: "The event is stored in UTC with the event's IANA zone, so the public page formats 7:00 p.m. New York correctly in March and January. The organizer route loads the event and compares `organizerId` to the session user before any write. The public catalogue starts from `status = PUBLISHED`, so a draft is invisible even at a direct URL. The cover is in object storage; the database stores only the key and the API checks the prefix before saving it." Each sentence names a mechanism and a failure it prevents.

If a check fails, do not move on and hope Week 2 will fix it. A missing ownership check becomes a data leak. A missing time-zone test becomes a support incident. A public catalogue that leaks drafts becomes a privacy problem. Week 2 adds concurrency and money; it does not repair the foundation silently.

## What the code should prove

The organizer route should demonstrate three checks in order: the session is valid, the user is an organizer, and the event belongs to that organizer. The public route should demonstrate the opposite discipline: it exposes only published events, and it does not require a session.

The event creation form should send ISO instants with an explicit offset plus the IANA zone. The API should validate the zone, the start/end relationship, and the sale window. The public page should format the instant in the event zone. A winter date and a summer date should both render the expected local time.

The ticket-type form should reject negative prices, zero capacity, a per-order limit above capacity, and a sale window outside the event. The publish endpoint should reject an event with no tiers. These are not edge cases; they are the minimum conditions for a product that can be sold.

The cover upload should prove the storage boundary: the browser receives a short-lived presigned URL, uploads directly to storage, and the API saves only the object key. A client-supplied key should be rejected. A non-image content type should be rejected.

The catalogue should prove visibility: a published event appears, a draft does not, and a cancelled event does not. Search and pagination should return a predictable envelope. A leading-wildcard search may scan; that is acceptable at this scale, and the limitation is documented.

## Common Week 1 failures

**The draft is visible by direct URL.** The public detail query does not filter `status = PUBLISHED`. Fix the query, not the link.

**The event time is wrong by an hour.** The form sent a local timestamp without a zone, or the page formatted the UTC instant without the event zone. Store UTC plus the IANA zone.

**The organizer list shows every event.** The query is missing `where: { organizerId: user.id }`. This is an object-level authorization bug even though it is a read.

**The ticket price is a float.** The API accepted `19.99` and stored it as a floating-point number. Use integer cents and reject non-integers.

**Publish succeeds with no ticket types.** The readiness check is missing. The public page has no way to buy; the event is a shell.

**The cover is a base64 string.** The image is in the database. Move the bytes to object storage and store the key.

**The catalogue returns a draft.** The visibility filter is in the UI or in a different query. Put it in the public query.

**The gate passes only on the happy path.** There are no tests for the wrong role, the wrong owner, the invalid time zone, or the duplicate tier. The gate is not proven.

## Week 1 gate

- [ ] The organizer can sign up, verify, onboard, create, publish, and upload a cover.
- [ ] The event stores UTC instants and the IANA zone; the public page shows the correct local time.
- [ ] The ticket-type validation rejects negative prices, zero capacity, max-per-order above capacity, and invalid sale windows.
- [ ] The public catalogue and direct event URL expose only published events.
- [ ] Another organizer cannot edit the event; an attendee cannot create one.
- [ ] The cover upload uses a presigned URL and stores only the object key.
- [ ] Search and pagination return a predictable envelope; the limit is capped.
- [ ] The course audit passes for Week 1 or every remaining flag has an accepted reason.
- [ ] The API and web app run from a clean checkout with the documented commands.
