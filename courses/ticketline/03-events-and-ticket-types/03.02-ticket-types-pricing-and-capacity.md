# 3.2 — Ticket types, pricing, and capacity

> **[Build]** · Module 03 — Events and ticket types · *The price at purchase must never change after the fact*

## The price that changed after purchase

An organizer sells 40 early-bird tickets at $45. A week later they raise the price to $60. A buyer opens an old order and sees $60. The buyer paid $45; the receipt now says $60. Support has to reconcile the difference manually.

The fix is not to freeze the ticket type forever. Organizers need to change prices for future sales. The fix is to snapshot the price at the moment the buyer commits: on the hold, and again on the order. The ticket type can change; the order must not.

This is the same pattern as a product catalog. The catalog price is current; the invoice price is historical. A ticketing platform needs both.

## The ticket type contract

A ticket type belongs to an event and carries:

| Field | Meaning | Rule |
|---|---|---|
| `name` | Display name, e.g. "Early Bird" | 2–60 characters; unique per event |
| `priceCents` | Price in integer cents | ≥ 0; no floats |
| `currency` | ISO currency code | `USD` for the course |
| `capacity` | Total inventory for this tier | ≥ 1 |
| `soldQuantity` | Units sold | ≥ 0 |
| `heldQuantity` | Units held | ≥ 0 |
| `maxPerOrder` | Maximum units in one purchase | 1..capacity |
| `salesStartAt` / `salesEndAt` | Tier sale window | Must fit inside the event sale window |

The counters are denormalized. `sold + held <= capacity` is the invariant. The write path that updates them atomically arrives in Module 4; in Week 1 they stay at zero.

Why keep `sold` and `held` separate instead of one `available` number? Because they mean different things and fail differently. A sold unit is revenue and a commitment. A held unit is a temporary claim that may disappear. If you collapse them into one number, you cannot answer "how many tickets did we sell?" without another source, and you cannot release an expired hold without guessing. The two counters preserve the history of the decision.

The math is simple but easy to get wrong. `available = capacity - sold - held`. The value should never be negative. If it is, the write path has a bug, and the public page should show sold out and log the violation rather than displaying a negative count. Do not clamp a broken counter to zero and hide the bug; fix the transaction.

The public UI should show `available`, not the raw counters, and it should show a sold-out state when the value is zero. The organizer dashboard can show `capacity`, `sold`, and `held` because the organizer needs the operational picture. The buyer needs one number and a clear action. Different audiences, different projections.

Create the shared schema:

```ts
export const ticketTypeInputSchema = z
  .object({
    name: z.string().trim().min(2).max(60),
    description: z.string().trim().max(500).optional(),
    priceCents: z.number().int().min(0).max(1_000_000),
    capacity: z.number().int().min(1).max(100_000),
    maxPerOrder: z.number().int().min(1).max(20),
    salesStartAt: z.coerce.date(),
    salesEndAt: z.coerce.date(),
  })
  .refine((value) => value.maxPerOrder <= value.capacity, {
    message: "The per-order limit cannot exceed capacity.",
    path: ["maxPerOrder"],
  })
  .refine((value) => value.salesEndAt > value.salesStartAt, {
    message: "The ticket sale window is invalid.",
    path: ["salesEndAt"],
  });
```

The API re-validates. The web form can show a friendly message, but the server is the boundary. Do not accept a float and round it silently; reject it. A price of `19.999` is a bug, not a value to coerce.

## The inventory states

  legend="The counters move between available, held, and sold. A hold is not a sale; a sale is not reversible without a refund policy."

The diagram separates three concepts that are easy to conflate:

- **Available** is derived: `capacity - sold - held`.
- **Held** is a temporary claim with an expiry.
- **Sold** is a confirmed order.

A UI that treats a hold as a sale will show "sold out" while a buyer is still paying. A UI that treats a sale as a hold will let a paid ticket expire. The states keep the product honest.

A worked example with numbers: a tier has capacity 900, sold 899, held 0. The page shows one available. Buyer A creates a hold for one, so held becomes 1 and available becomes 0. Buyer B sees sold out and is told to try another tier or wait for the hold to expire. If A pays, sold becomes 900 and held becomes 0; the ticket is issued. If A abandons the hold, it expires, held becomes 0, and available returns to 1. The total sold never changes in the abandoned case; the hold was never a sale.

The last step is where many implementations fail. A hold expiry job that decrements `sold` instead of `held` corrupts the revenue count. A payment confirmation that increments `sold` but forgets to decrement `held` double-counts the unit and makes the tier look sold out. Module 4 writes these transitions in one transaction and tests both paths. The schema only defines the counters; the transition logic is the product.

## Create and update

`POST /organizer/events/:id/ticket-types` loads the event, checks ownership, validates the input, and inserts:

```ts
const event = await loadOwnedEvent(req.user!, req.params.id);
const input = ticketTypeInputSchema.parse(req.body);

if (input.salesStartAt < event.salesStartAt || input.salesEndAt > event.salesEndAt) {
  return res.status(400).json({
    success: false,
    message: "The ticket sale window must fit inside the event sale window.",
    code: "INVALID_SALE_WINDOW",
  });
}

const ticketType = await prisma.ticketType.create({
  data: { ...input, eventId: event.id },
});
```

`PATCH /organizer/events/:id/ticket-types/:ticketTypeId` uses `findFirst({ where: { id, eventId } })` so the ticket type and the event are checked together. The unique constraint on `(eventId, name)` prevents duplicate tiers; translate Prisma `P2002` into `409 TICKET_TYPE_EXISTS`.

Do not let an organizer change `capacity` below `sold + held`. The check belongs in the update path even before the counters move; when they do, it becomes critical.

## Publish readiness

Publish must reject an event with no ticket types, a zero-capacity tier, or an invalid sale window. Add those checks to `assertEventReady` from 3.1. A published event with no way to buy is a shell, not a product.

A useful error tells the organizer exactly what to fix:

```
422 EVENT_NOT_READY
"Add at least one ticket type."
```

Not:

```
400 Bad Request
```

The first is actionable. The second makes the organizer guess.

## The price snapshot

In Module 4, a hold will store `priceCents` and `currency` at creation. In Module 5, the order will store the same values plus the ticket-type name. The ticket type remains mutable for future sales; the order remains evidence of the past.

Write the decision in `docs/decisions.md`:

> Ticket types are mutable. Holds and orders snapshot the price at the moment of commitment. A later price change never rewrites an existing order.

The same rule applies to the event date, venue, and ticket-type name. A buyer's confirmation should show what they bought, not what the organizer changed it to later.

## Alternatives and trade-offs

**Integer cents vs decimal.** Use integer cents. A `Decimal` type is also valid, but it adds a library and a serialization decision. Cents are simple and exact for a single currency. If you add multi-currency, store the minor unit and the currency's exponent.

**Derived counters vs aggregates.** You could compute `sold` and `held` from the orders and holds tables on every read. That is always correct but slow at scale. The counters are a read optimization; the write path must keep them correct in the same transaction.

**One ticket type vs many.** A single "General Admission" tier is simpler. The course uses multiple tiers because real events have early bird, standard, and VIP, and the pricing/limit rules are part of the lesson.

**Reserved seating.** A seat map is a different inventory model: each seat is an entity, not a fungible unit. The core course uses general admission. Seat maps belong to the Sports and Cinema variants.

## What can go wrong

**Floating-point prices.** `19.99` becomes `19.989999...`. Store cents.

**Capacity below sold/held.** An update that reduces capacity can violate the invariant. Check `capacity >= sold + held` before the update.

**Sale window outside the event.** A tier that sells after the event starts creates a confusing page. Validate the relationship.

**Max per order above capacity.** A buyer can never purchase more than capacity. Reject the tier at creation.

**Duplicate tier names.** Two "VIP" tiers confuse the buyer and the reports. Use the unique constraint.

**Price changes rewriting history.** Reading the current ticket-type price on an old order changes the receipt. Snapshot.

**Publishing with no tier.** The public page has no way to buy. Reject publish with `422`.

**Lowering capacity after sales.** An organizer may want to reduce capacity after tickets are sold. A blind update can set capacity below `sold + held`, which breaks the invariant and makes the public count negative. The update must check the current counters and reject the change with a clear message. If the organizer needs to stop sales, close the sale window or mark the tier sold out; do not rewrite history by shrinking capacity below what was already sold.

**Changing the per-order limit after sales.** Raising the limit is usually safe. Lowering it below an existing order's quantity does not invalidate the order; it only changes future purchases. The API should allow the change but the UI should explain that existing orders are unaffected. The order is evidence of what was allowed at the time.

## Build

1. Add the shared ticket-type schema.
2. Implement create and update routes with event ownership.
3. Validate the tier sale window against the event sale window.
4. Add the duplicate-name error mapping.
5. Extend `assertEventReady`.
6. Build the organizer form for adding and editing tiers.
7. Keep the counters at zero until Module 4; add a comment in the code that the write path owns them.

Acceptance criteria:

- A price of `-1` returns `400`.
- A capacity of `0` returns `400`.
- `maxPerOrder > capacity` returns `400`.
- A sale window outside the event window returns `400`.
- Two tiers with the same name on one event return `409`.
- An event with no tiers fails to publish with `422`.
- The public response shows the tier price in cents and a formatted display value.

## Verify

Unit-test the schema with boundary values. Then create an event, add a valid tier, and publish. Add a second tier with the same name and expect `409`. Try a zero-capacity tier and expect `400`.
