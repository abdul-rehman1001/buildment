# 2.4 — Organizer onboarding, email verification, and auth tests

> **[Check]** · Module 02 — Auth and roles · *Becoming an organizer is a transition you can audit*

## Anyone can sign up; not everyone should publish

If signup lets a user choose `role: "ORGANIZER"`, anyone can publish events. If the role is set by a hidden checkbox, the client can change it. The production pattern is an explicit onboarding flow:

1. Signup creates an `ATTENDEE`.
2. The attendee verifies their email.
3. The attendee creates an organizer profile.
4. The API upgrades the role to `ORGANIZER` and records the profile.

The role change is server-side and auditable. The client never sends the role. This chapter builds that flow and then proves the whole auth module with tests.

## Why verify the email?

An organizer publishes public events, receives buyer messages, and eventually receives payouts. An unverified email makes account recovery, impersonation, and spam easier. Verification also proves that the person controls the address before they can act as a business on the platform.

The trade-off is friction. A buyer does not need to verify before browsing or holding a ticket. An organizer does. The course draws the line at the role transition, not at signup. That keeps the buyer flow fast and the organizer flow trustworthy.

The order is deliberate. A token that is used twice is rejected. An unverified user cannot create an organizer profile. A second onboarding request does not create a duplicate profile; the primary key on `OrganizerProfile.userId` prevents it.

## The token model

Add an `OrganizerProfile` model:

```prisma
model OrganizerProfile {
  userId      String   @id
  displayName String
  bio         String?
  website     String?
  createdAt   DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

Add the inverse relation to `User`:

```prisma
organizerProfile OrganizerProfile?
```

The verification token is random, hashed, single-use, and short-lived:

```ts
export function createVerificationToken() {
  return randomBytes(32).toString("base64url");
}

export function hashVerificationToken(token: string) {
  return createHash("sha256").update(token).digest("hex");
}
```

Store `tokenHash`, `userId`, `expiresAt`, and `usedAt`. The raw token is sent in the email link and never stored. The TTL is 30 minutes. A used token cannot be reused; an expired token is rejected with the same generic message, so an attacker cannot distinguish the two.

## Email delivery with a fallback

The course must be finishable without an email provider. In development, log the verification link. In production, send it with Resend.

```ts
const resend = env.RESEND_API_KEY ? new Resend(env.RESEND_API_KEY) : null;

export async function sendVerificationEmail(email: string, token: string) {
  const link = `${env.WEB_ORIGIN}/verify-email?token=${token}`;

  if (!resend) {
    logger.info({ email, link }, "verification email (dev fallback)");
    return;
  }

  await resend.emails.send({
    from: env.EMAIL_FROM,
    to: email,
    subject: "Verify your Ticketline email",
    text: `Verify your email: ${link}`,
  });
}
```

Never log the token in production. The fallback is gated by the absence of a provider key and is documented in the README. A learner who cannot create a Resend account can still complete the course.

The email link points to the web app, not the API. The web page reads `token` from the query string and posts it to the API. This keeps the token out of the API's own redirects and gives the web app a place to show a friendly success or failure state.

## The organizer onboarding transaction

The profile and the role change happen together:

```ts
const profile = await prisma.$transaction(async (tx) => {
  const created = await tx.organizerProfile.create({
    data: { userId: req.user!.id, ...input },
  });
  await tx.user.update({
    where: { id: req.user!.id },
    data: { role: "ORGANIZER" },
  });
  return created;
});
```

If the profile insert fails, the role does not change. If the role update fails, the profile does not stay. The transaction is the invariant: an organizer profile and the organizer role exist together.

If the user is already an organizer, return `409 ALREADY_ORGANIZER`. The primary key on `OrganizerProfile.userId` also prevents a duplicate; translate the Prisma unique error into a clear response.

## Testing the module

Use a separate test database. Tests that share the development database will eventually delete data you care about, and tests that run in parallel will interfere with each other.

Create `ticketline_test` once:

```bash
docker compose exec postgres createdb -U ticketline ticketline_test
DATABASE_URL=postgresql://ticketline:ticketline@localhost:5432/ticketline_test pnpm --filter api prisma migrate deploy
```

A test helper resets the tables between tests. The delete order is children before parents:

```ts
export async function resetDatabase() {
  await prisma.ticketType.deleteMany();
  await prisma.event.deleteMany();
  await prisma.organizerProfile.deleteMany();
  await prisma.emailVerificationToken.deleteMany();
  await prisma.session.deleteMany();
  await prisma.user.deleteMany();
}
```

Week 1 does not have holds, orders, tickets, or scans yet. Add those `deleteMany` calls when their models arrive in Week 2 so the helper keeps compiling.

Use a supertest agent so cookies persist across requests:

```ts
export function agent() {
  return request.agent(createApp());
}
```

### The tests that matter

1. **Signup sets a cookie and returns the user.** Assert `201`, `Set-Cookie`, and `HttpOnly`.
2. **Wrong password and unknown email return the same 401.** Assert status, message, and code.
3. **Logout revokes the session.** Call `/me` with the old agent; expect `401`.
4. **Session expiry.** Insert a session with `expiresAt` in the past; call `/me`; expect `401` and the row is deleted.
5. **Role matrix.** Attendee on an organizer route → `403`; owner → success; other organizer → `403`; admin → success.
6. **IDOR.** Create an event for organizer A; patch it with organizer B; expect `403 NOT_EVENT_OWNER`.
7. **Onboarding requires verification.** An unverified user gets `403 EMAIL_NOT_VERIFIED`; a verified user gets `201` and the role changes.
8. **Token reuse.** Verify the same token twice; the second request fails.
9. **Duplicate onboarding.** The second request returns `409`, not a second profile.

The tests are the evidence for the module gate. A successful manual demo is not enough; it does not prove the failure paths.

## What can go wrong

**Token reuse.** A used token that is not marked `usedAt` can be replayed. Mark it and check it in the same transaction as the user update.

**Unverified onboarding.** The handler checks the session but not `emailVerifiedAt`. A user can become an organizer without proving the email.

**Duplicate profiles.** The profile primary key prevents duplicates, but only if the handler catches the unique error and returns a clear response. Otherwise the user sees a `500`.

**Email fallback in production.** A missing provider key must not silently log links in production. Gate the fallback by `NODE_ENV !== "production"` and fail loudly in production if email is required.

**Flaky tests.** Shared state, parallel test files, and a shared database produce intermittent failures. Use one test database per worker or run the API tests serially. Reset between tests.

**Testing only the happy path.** The logout, expiry, IDOR, and duplicate-token tests are the ones that catch real bugs. A test suite that only signs up and logs in is a demo, not a safety net.

**Test data that looks like production.** Do not use real emails, phone numbers, or payment details in fixtures. Use `example.test` addresses and fake names.

## Build

1. Add the `OrganizerProfile` model and migrate.
2. Add the verification token helpers and the email sender with the console fallback.
3. Implement `request-verification`, `verify-email`, and `organizer/onboarding`.
4. Protect onboarding with `requireAuth` and the verified-email check.
5. Create the test database, vitest config, reset helper, and supertest agent.
6. Write the nine tests above.
7. Add the verification and onboarding pages to the web app.

Acceptance criteria:

- Signup → request verification → the dev log prints a link.
- The link marks the email verified and cannot be used twice.
- Onboarding before verification returns `403 EMAIL_NOT_VERIFIED`.
- Onboarding after verification creates a profile and changes the role to `ORGANIZER`.
- A second onboarding request returns `409` and does not create a duplicate.
- The client cannot set `role` in any request body.
- The auth test suite passes in CI.
