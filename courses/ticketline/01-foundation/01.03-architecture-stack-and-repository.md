# 1.3 — Architecture, stack, and repository

> **[Learn]** · Module 01 — Foundation · *Draw the system before you install a single package*

## The secret in the browser

A developer builds a checkout page and puts the Stripe secret key in a `NEXT_PUBLIC_` environment variable. The page works. Then someone opens the browser bundle and reads the key. The secret is now public, and the test account is compromised.

The mistake is architectural, not a typo. Secrets belong to the server. The browser gets a public key and a session cookie; it never gets a database URL, a Stripe secret, or an S3 secret. Once you understand that boundary, the stack choices become easier: the browser is a rendering and input surface, and the API owns every rule that matters.

## The request path

Ticketline uses two apps and one shared package:

- **Web:** Next.js renders the catalogue, organizer workspace, checkout, and scanner. It calls the API over HTTP.
- **API:** Express validates input, authenticates the session, enforces authorization, owns inventory and pricing, talks to Stripe, and writes the database.
- **Shared:** Zod schemas and TypeScript types used by both apps.

A browser request to `GET /api/v1/events` does not talk to Postgres. It goes to the Next.js server, which proxies the request to the Express API. The API validates the query, reads Postgres, and returns the `{ success, data }` envelope. The browser renders the result.

This is the default path for every read. A write adds authentication, authorization, validation, and a transaction. The web app never imports the database client and never owns a business rule. If a rule matters, it lives on the API side of the trust boundary.

## Why split the web and the API?

A single Next.js app with server actions is a valid architecture. This course splits them for three reasons:

1. **The trust boundary becomes visible.** You write the API authorization and see that the browser cannot enforce it.
2. **The deployment boundary becomes real.** Web and API can scale and deploy independently.
3. **The tests become cheaper.** The API is a plain Express app; supertest exercises it without a browser.

The cost is setup time. The monorepo and shared package below are designed to keep that cost small. If you are building alone and want the shortest path, a single Next.js app is a reasonable alternative. The course keeps the split because the project is meant to demonstrate production boundaries, not because Next.js cannot do both.

The split also changes where you debug. A browser error is a rendering problem; an API error is a contract or data problem; a database error is a schema or transaction problem. When the apps are separate, the boundary is visible in the logs. When they are one app, a server action can hide a slow query, a validation error, and a rendering failure in the same stack trace. For a course about production behavior, the separation is worth the setup.

The shared package is the contract between the two apps. Put the Zod schemas and the TypeScript types there, and import them from both sides. If the web app defines its own copy of `eventInputSchema`, the two copies will drift. The typecheck will pass in both apps while the API rejects a field the web app still sends. A shared contract makes that drift a compile error.

## The stack

| Concern | Choice | Why | Alternative |
|---|---|---|---|
| Web | Next.js 16 App Router | Server rendering, routing, and a simple proxy | Vite + React SPA |
| API | Express 5 + TypeScript | Clear middleware and route boundaries; easy to test | Fastify, Hono, NestJS |
| Database | PostgreSQL 16 + Prisma 7 | Relational invariants, transactions, migrations | MongoDB, raw SQL |
| Queue | Redis 7 + BullMQ | Delayed hold expiry and retries | Database polling, SQS |
| Payments | Stripe test mode | Realistic checkout and webhooks without real money | Fake checkout, Paddle |
| Storage | S3-compatible (R2/S3/MinIO) | Event images without database bloat | Cloudinary |
| Email | Resend, console fallback | Ticket delivery without blocking local dev | Postmark, SES, SMTP |
| Tests | Vitest + supertest + Playwright | Unit, API, and browser coverage | Jest, Node test runner |

The exact versions matter less than the boundaries. Pin them in `package.json`, run the commands, and do not claim a version you have not executed. The technical validator will re-run the commands before publish.

### PostgreSQL over MongoDB

The core lesson is a relational invariant under concurrency: conditional updates, row locks, and transactions. PostgreSQL gives you those tools directly. MongoDB can model the same domain, but the course's schema and tests are written for Postgres. If you are already fluent in MongoDB, the data model will translate; the concurrency tests will need different tools.

### BullMQ over polling

A hold expires at a known time. Polling every 30 seconds means a seat can remain locked for 30 seconds after expiry, which is visible during a scarce on-sale. A delayed job fires close to the expiry time. BullMQ adds Redis, but the course already needs Redis for rate limits and queues in Week 2. If you want to avoid Redis, a database poll is a valid v1 compromise; document the added latency.

### S3 over database blobs

Event covers are bytes. Storing them in a `bytea` column makes every query and backup heavier. Object storage keeps the database small and lets a CDN serve the image. MinIO gives you an S3-compatible local target without a cloud account.

The shared package holds Zod schemas and types. The API and web app import the same contract, so a field rename fails at typecheck time instead of at runtime. The apps remain independently deployable; the shared package is copied or built as part of each app, not a runtime service.

The deployment topology mirrors the repository. The web app can deploy to Vercel, the API and worker to Render or Fly, Postgres and Redis to a managed service, and object storage to R2 or S3. The API is the only service that knows the database URL. The web app knows only the API URL. The worker shares the API's database and queue credentials, but it does not serve HTTP. If you deploy everything as one process, you lose the ability to scale the worker separately, and a long-running job can starve the API's event loop.

The local topology should be a smaller version of the production topology, not a different architecture. Docker Compose gives you Postgres, Redis, and MinIO on the same ports the production services use conceptually. The same `DATABASE_URL`, `REDIS_URL`, and S3 variables point at local containers in development and managed services in production. A learner who only runs a SQLite file locally will discover the differences in Week 2, when the concurrency and queue behavior matter.

### Monorepo vs two repositories

A monorepo gives you one install, one CI workflow, and a shared contract. A pair of repositories gives you clearer ownership and independent deploys, but you must publish or duplicate the contract. For a solo four-week build, the monorepo is the lower-friction choice. If you already have a team and two deploy pipelines, split the repos.

### Environment variables

Create `.env.example` at the root. Do not commit `.env`.

```
DATABASE_URL=postgresql://ticketline:ticketline@localhost:5432/ticketline
PORT=4000
WEB_ORIGIN=http://localhost:3000
API_URL=http://localhost:4000
REDIS_URL=redis://localhost:6379
S3_ENDPOINT=http://localhost:9000
S3_REGION=us-east-1
S3_ACCESS_KEY=minio
S3_SECRET_KEY=minio-secret
S3_BUCKET=ticketline
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
RESEND_API_KEY=
EMAIL_FROM=Ticketline <tickets@example.test>
```

The API reads and validates its variables at boot. The web app only needs `API_URL` for the server-side proxy. No secret gets a `NEXT_PUBLIC_` prefix.

## Scaffold the workspace

Create the root and the workspace file:

```bash
mkdir ticketline && cd ticketline
pnpm init
mkdir -p apps packages/shared/src
```

`pnpm-workspace.yaml`:

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

Root scripts:

```json
{
  "name": "ticketline",
  "private": true,
  "packageManager": "pnpm@10",
  "scripts": {
    "dev": "pnpm -r --parallel dev",
    "build": "pnpm -r build",
    "typecheck": "pnpm -r typecheck",
    "test": "pnpm -r test",
    "db:migrate": "pnpm --filter api prisma migrate dev"
  }
}
```

Create the web app and the API:

```bash
pnpm create next-app@latest apps/web --typescript --tailwind --eslint --app --src-dir --import-alias "@/*" --use-pnpm
mkdir -p apps/api/src apps/api/prisma
cd apps/api
pnpm init
pnpm add express@5 cors cookie-parser helmet pino pino-http zod @prisma/client @prisma/adapter-pg
pnpm add -D typescript tsx prisma @types/express @types/cors @types/cookie-parser @types/node vitest supertest @types/supertest
```

Add `"type": "module"` and the API scripts:

```json
{
  "type": "module",
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc -p tsconfig.json",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "prisma": "prisma"
  }
}
```

Add `docker-compose.yml` with Postgres, Redis, and MinIO. The exact compose file is in `1.4`; for now, the important part is that all three services start with one command and expose the ports in `.env.example`.

## A worked example: where does a rule live?

Suppose the organizer dashboard needs a "publish event" button. The browser can show a button, disable it while a request is in flight, and render an error. It must not decide whether the event is publishable.

The API should:

1. Authenticate the session.
2. Load the event and check ownership.
3. Verify the event has at least one ticket type and a valid sale window.
4. Check the status transition.
5. Update the event in a transaction.
6. Return a specific error when a condition fails.

The web app calls the API and renders the result. If you move step 3 into the web app, a second client (curl, a mobile app, a test) can bypass it. If you move step 2 into the web app, a second client can publish someone else's event. The rule lives on the API side of the boundary.

## What can go wrong

**Secrets in the client bundle.** A `NEXT_PUBLIC_` secret is public. Keep Stripe, database, S3, and email credentials server-only.

**Direct database access from the browser.** A browser cannot reach Postgres in production, but a learner might expose a database URL in a client component or a server action that runs on the client. Keep the Prisma client in `apps/api`.

**CORS and cookies.** A same-origin proxy avoids most CORS pain. If you call the API host directly from the browser, configure `CORS_ORIGINS` with credentials and a cookie policy that matches the deployment. `SameSite=Lax` does not work across unrelated domains.

**Environment drift.** The web app and API read different env files. Name the variables consistently and validate them at boot. A missing `DATABASE_URL` should fail immediately, not on the first request.

**Shared contract drift.** If the web app duplicates the Zod schema instead of importing it, the two copies diverge. Put the schema in `packages/shared` and import it from both apps.

**Deployment mismatch.** A local proxy that works at `localhost:3000` can fail behind a production domain if cookies, CORS, or the API URL are wrong. Test the deployed path before the demo.

## Build

1. Create the workspace, apps, and shared package.
2. Add `docker-compose.yml` and `.env.example`.
3. Configure the Next.js rewrite from `/api/:path*` to `${API_URL}/api/:path*`.
4. Add a placeholder API health route and a placeholder web page.
5. Add the root scripts for dev, typecheck, test, and migrate.

Acceptance criteria:

- `pnpm install` completes from the root.
- `docker compose up -d` starts Postgres, Redis, and MinIO.
- `pnpm --filter web dev` starts Next.js on `:3000`.
- `pnpm --filter api dev` starts the API on `:4000`.
- No secret appears in a `NEXT_PUBLIC_` variable.
- The shared package is imported by at least one API and one web file.

## Verify

```bash
pnpm install
docker compose up -d
pnpm --filter api dev
pnpm --filter web dev
```

Then open `http://localhost:3000` and confirm the placeholder page loads. Open `http://localhost:4000/health` and confirm the API responds. If the web page calls the API, use the same-origin `/api` path, not `http://localhost:4000` directly.
