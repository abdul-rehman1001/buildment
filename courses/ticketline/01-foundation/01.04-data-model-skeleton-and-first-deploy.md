# 1.4 — Data model, migrations, and the running skeleton

> **[Build]** · Module 01 — Foundation · *The schema is the last line of defense*

## The column that should not exist

A common first schema stores `available_tickets` on the event and decrements it from the API:

```ts
await db.event.update({
  where: { id: eventId },
  data: { availableTickets: { decrement: quantity } },
});
```

It looks correct until two requests run at the same time. Both read 1, both decrement, and the column reaches -1. The bug is not the `decrement`; the bug is that the invariant is represented as a mutable number with no guard.

The schema must make the invariant explicit: capacity is fixed, sold and held are tracked separately, and a constraint or conditional update ensures they never exceed capacity. The database is the last line of defense. Even if an API handler has a bug, the schema should make the invalid state difficult or impossible to write.

## The Week 1 tables

The first version of the schema has five tables. They are enough to publish an event and test the authorization model; holds, orders, tickets, and scans arrive in Week 2.

| Table | Purpose | Invariant |
|---|---|---|
| `users` | Identity, role, verification | Email is unique; role is one of four values |
| `sessions` | Opaque session tokens | Token hash is unique; expired sessions are rejected |
| `email_verification_tokens` | Single-use email verification | Token hash is unique; a token is used once |
| `events` | Organizer-owned events | Slug is unique; only an owner can edit |
| `ticket_types` | Priced capacity for an event | `sold_quantity + held_quantity <= capacity` |

The diagram shows the relationships; the table below explains why each field exists.

### Users

`User` carries the identity and the global role. `email` is unique and normalized to lowercase. `passwordHash` stores an Argon2id hash, never the plaintext. `emailVerifiedAt` is nullable; the organizer onboarding flow requires it. The role enum is `ATTENDEE`, `ORGANIZER`, `GATE_STAFF`, or `ADMIN`.

### Sessions

`Session` stores a hash of the session token, the user, and an expiry. The raw token is sent to the browser in an HttpOnly cookie and never stored in the database. The unique index on `token_hash` makes lookup fast and prevents duplicate rows. The `expires_at` index supports cleanup and expiry checks.

### Email verification tokens

`EmailVerificationToken` stores a hash, a user, an expiry, and a `usedAt` timestamp. A token is single-use. The hash means a database leak does not expose working verification links. The TTL is short — 30 minutes in this course — because the user is already signed in when they request it.

### Events

`Event` is owned by an organizer. The slug is unique and shareable. `timezone` stores an IANA zone such as `America/New_York`; the instants are stored in UTC. `status` is an enum: `DRAFT`, `PUBLISHED`, `CANCELLED`, `COMPLETED`. `cover_image_key` stores the object key, not the image bytes. The indexes support the organizer's list and the public catalogue.

### Ticket types

`TicketType` belongs to an event. `price_cents` is an integer, `capacity` is the total inventory, and `sold_quantity` and `held_quantity` are denormalized counters. The invariant is `sold + held <= capacity`. `max_per_order` limits a single purchase. The `(eventId, name)` unique constraint prevents duplicate tiers.

## Three modelling decisions

### Money is an integer number of cents

Use `priceCents Int`, not a floating-point dollar amount. `19.99` is not exactly representable in binary floating point; a cent lost or gained in a price calculation is a support ticket. Format at the edge, store an integer.

### Instants are UTC; display uses the event zone

Store `startsAt`, `endsAt`, and sale windows as `DateTime` in UTC. Store the event's IANA zone for display and validation. A timestamp without a zone is a bug waiting for a daylight-saving transition. A fixed offset is also wrong half the year; the named zone carries the rules.

### Status is an enum

`DRAFT`, `PUBLISHED`, `CANCELLED`, `COMPLETED` are a closed set. An enum in PostgreSQL prevents a typo from creating an unreachable state. The transition rules still live in the API; the enum only guarantees the vocabulary.

## The Prisma schema

Create `apps/api/prisma/schema.prisma`:

```prisma
generator client {
  provider = "prisma-client-js"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

enum Role {
  ATTENDEE
  ORGANIZER
  GATE_STAFF
  ADMIN
}

enum EventStatus {
  DRAFT
  PUBLISHED
  CANCELLED
  COMPLETED
}

model User {
  id                 String   @id @default(cuid())
  email              String   @unique
  name               String
  passwordHash       String
  role               Role     @default(ATTENDEE)
  emailVerifiedAt    DateTime?
  createdAt          DateTime @default(now())
  updatedAt          DateTime @updatedAt

  sessions           Session[]
  verificationTokens EmailVerificationToken[]
  events             Event[]

  @@index([role])
}

model Session {
  id        String   @id @default(cuid())
  tokenHash String   @unique
  userId    String
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
}

model EmailVerificationToken {
  id        String    @id @default(cuid())
  tokenHash String    @unique
  userId    String
  expiresAt DateTime
  usedAt    DateTime?
  createdAt DateTime  @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}

model Event {
  id            String      @id @default(cuid())
  organizerId   String
  slug          String      @unique
  title         String
  description   String
  venueName     String
  venueAddress  String
  timezone      String
  startsAt      DateTime
  endsAt        DateTime
  salesStartAt  DateTime
  salesEndAt    DateTime
  status        EventStatus @default(DRAFT)
  coverImageKey String?
  createdAt     DateTime    @default(now())
  updatedAt     DateTime    @updatedAt

  organizer   User         @relation(fields: [organizerId], references: [id], onDelete: Cascade)
  ticketTypes TicketType[]

  @@index([organizerId])
  @@index([status, startsAt])
}

model TicketType {
  id           String   @id @default(cuid())
  eventId      String
  name         String
  description  String?
  priceCents   Int
  currency     String   @default("USD")
  capacity     Int
  soldQuantity Int      @default(0)
  heldQuantity Int      @default(0)
  maxPerOrder  Int      @default(4)
  salesStartAt DateTime
  salesEndAt   DateTime
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  event Event @relation(fields: [eventId], references: [id], onDelete: Cascade)

  @@unique([eventId, name])
  @@index([eventId])
}
```

The counter columns are denormalized on purpose: the public page should not aggregate every order on every read. The write path that keeps them correct arrives in Module 4. Until then, they stay at zero, and the public page shows capacity.

Denormalization is a trade. The normalized version stores only holds and orders and computes `sold` and `held` with an aggregate. It is always consistent and easy to reason about, but every public page read pays for the aggregate, and the query gets worse as orders grow. The counter version is fast to read but must be updated in the same transaction as the hold or order. If the update is missing, the counter drifts. If it is outside the transaction, a crash can leave the counter and the rows inconsistent.

The course chooses counters because the public page and the last-ticket race are the hot paths. The invariant test is the guard: after every write, `sold + held <= capacity`. If the counter is wrong, the test fails. A repair job that recomputes counters from holds and orders is a useful Week 4 addition; it is not a substitute for the transaction.

The counters also make the failure mode visible. A blind `increment` has no condition. The conditional update in Module 4 will look like `WHERE sold_quantity + held_quantity + $1 <= capacity`; if zero rows change, the claim lost. That single predicate is the difference between a counter and an invariant.

## Prisma 7 config and migration

Prisma 7 expects the connection URL in `prisma.config.ts`, not in `schema.prisma`:

```ts
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations" },
  datasource: { url: process.env.DATABASE_URL! },
});
```

Run the first migration:

```bash
pnpm --filter api prisma migrate dev --name init
```

Open Prisma Studio and inspect the tables:

```bash
pnpm --filter api prisma studio
```

A migration is a versioned change. If you edit the schema later, create a new migration; do not edit an applied migration file. If a migration fails in production, the deploy should stop before the app starts serving traffic.

Migration safety is a production concern, not a Prisma detail. A migration that adds a required column to a table with rows will fail unless it has a default or a backfill. A migration that renames a column can break the previous API version during a rolling deploy. A migration that drops a column can destroy data that a rollback still needs. For the course, keep migrations additive and small. Add a nullable column, backfill it, then make it required in a later migration. Do not combine a schema change and a data migration in one irreversible step.

The first migration is also a checkpoint. Commit the `prisma/migrations` folder. A teammate who clones the repository should run `prisma migrate deploy` and get the same schema, not a manual sequence of SQL statements. If the migration folder is missing, the schema exists only on your machine.

## The running skeleton

The API needs five pieces before it can be tested:

1. **Config.** Parse and validate environment variables at boot. A missing `DATABASE_URL` should fail immediately with a readable message.
2. **Database client.** One Prisma client per process, using the `@prisma/adapter-pg` adapter in Prisma 7.
3. **Health route.** `GET /health` should query `SELECT 1`, not only return `{ status: "ok" }`.
4. **Error handler.** One envelope: `{ success: false, message, code }`. Do not leak stack traces in production.
5. **App factory.** Export `createApp()` without listening, so supertest can drive it.

A minimal health test:

```ts
import request from "supertest";
import { describe, expect, it } from "vitest";
import { createApp } from "../app.js";

describe("GET /health", () => {
  it("returns ok when the database is reachable", async () => {
    const response = await request(createApp()).get("/health");
    expect(response.status).toBe(200);
    expect(response.body.status).toBe("ok");
  });
});
```

The web app needs a same-origin proxy. In `apps/web/next.config.ts`:

```ts
const nextConfig = {
  async rewrites() {
    return [{ source: "/api/:path*", destination: `${process.env.API_URL}/api/:path*` }];
  },
};
export default nextConfig;
```

A placeholder page that fetches `/health` through the server proves the path works. Do not stop at a page that renders static text; the point of the skeleton is to prove the boundary.

Add a CI workflow that installs dependencies, generates the Prisma client, typechecks, and runs the health test. The first CI job does not need Redis or MinIO because the skeleton does not use them yet. Add those services when the code needs them.

## What can go wrong

**Missing generated client.** `Cannot find module './generated/prisma/index.js'` means `prisma generate` has not run. Add it to the build and CI steps.

**SSL against local Postgres.** In production, the API may force TLS. Local Postgres does not support SSL. Guard the SSL option by environment; do not set it unconditionally.

**Migration drift.** A schema change without a migration means local and production diverge. Run `prisma migrate dev` locally and `prisma migrate deploy` in deploy.

**Environment mismatch.** `DATABASE_URL is required` usually means the API is running from the wrong directory or `.env` is missing. Validate at boot and print the file it expects.

**Health check that lies.** A route that returns `ok` without touching the database can pass while the database is down. Query the database.

**Proxy mismatch.** The web app calls `http://localhost:4000` directly in one component and `/api` in another. Pick the same-origin proxy for browser calls and keep the API URL server-side.

## Build

1. Create the Prisma schema and `prisma.config.ts`.
2. Add `DATABASE_URL` to `apps/api/.env`.
3. Run the init migration and generate the client.
4. Add the config, database client, logger, health route, error handler, and app factory.
5. Add the web proxy and a page that fetches `/health`.
6. Add the health test and the CI workflow.
7. Commit the migration files.

Acceptance criteria:

- `GET /health` returns `200` and checks the database.
- The web page shows the API status.
- `prisma migrate dev` reports no changes on a second run.
- The health test passes in CI.
- No `.env` file is tracked.
- The ERD and permission matrix are committed in `docs/`.

## Verify

```bash
docker compose up -d
pnpm --filter api prisma migrate dev --name init
pnpm --filter api dev
pnpm --filter web dev
curl -s http://localhost:4000/health
```

Expect `{"status":"ok","timestamp":"..."}`. Stop Postgres and call the health route again; it should return a `500`, not a fake `ok`. Restart Postgres and confirm recovery.
