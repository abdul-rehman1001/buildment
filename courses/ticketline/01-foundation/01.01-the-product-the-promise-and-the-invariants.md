## Two buyers, one ticket

At 10:00:00.000, a 900-seat venue has one ticket left. Two buyers press **Pay** within 180 milliseconds of each other. Both requests reach your API. Both see one available ticket. Both write an order.

One of those buyers will arrive at the venue with a valid-looking ticket and no seat. The other will discover the problem at the gate. The refund is annoying; the trust damage is worse. The organizer now has to explain to a customer why the platform sold something it did not have.

This is the moment Ticketline exists to survive. Everything else — the event page, the organizer dashboard, the QR code, the receipt — is scaffolding around that moment. If your system cannot answer "who gets the last ticket?" correctly, it is a demo, not a ticketing platform.

The course is built around that promise. You will not learn every feature of a commercial ticketing company. You will learn how to make one purchase-and-entry loop trustworthy under concurrency, retries, abuse, and a bad network at the venue. That is a smaller goal, and a much harder one.

## What Ticketline is

Ticketline is a ticketing platform for small and mid-sized venues. An organizer publishes an event with ticket types and a capacity. A buyer holds inventory, pays with Stripe test mode, and receives a QR ticket. Gate staff scan the ticket at the door. The organizer sees sales and check-ins.

The product has four surfaces:

- **Organizer workspace:** create and publish events, define ticket types, see sales and check-ins.
- **Public catalogue:** find a published event and open its page.
- **Buyer checkout:** select tickets, hold them, pay, and receive a ticket.
- **Gate scanner:** validate a ticket and record the entry, including when the network is down.

The course deliberately keeps the surfaces small. There is no recommendation engine, no resale marketplace, no dynamic pricing, and no native mobile app. Those features are expensive to build and distract from the invariants that make the core loop trustworthy.

## The four invariants

An invariant is a rule that must stay true at every moment, no matter which requests arrive at the same time. Ticketline has four. They are not slogans; they become database constraints, API checks, and tests.

1. **No overselling.** For every ticket type, `sold_quantity + held_quantity <= capacity` at every instant. The database decides who wins the last ticket, not the browser.
2. **One paid order, one set of tickets.** A duplicate payment webhook must not create a second order or a second ticket. Payment confirmation is idempotent.
3. **One ticket, one entry.** A ticket admits one attendee once. A duplicate scan is recorded as a duplicate and rejected; it is not silently ignored.
4. **One organizer, one event.** An organizer can read and mutate only their own events. A gate staff member can scan only assigned events. Authentication is not authorization.

Each invariant has a failure story. A sold-out seat with two buyers. A webhook that arrives twice. A ticket screenshot shared with a friend. An event ID changed in a URL. The course is a sequence of decisions that make those stories impossible, or at least detectable and recoverable.

Write the invariants down before you write code. In the next chapters, you will map each one to a table, a constraint, or a test. If you cannot point to the mechanism that protects an invariant, it is only a wish.

## The five-minute demo

By the end of the course, you will run this demo without notes:

1. An organizer creates and publishes an event with two ticket types and a capacity.
2. Two buyers race for the last ticket. One gets a hold; the other gets a clear conflict.
3. The winner pays with a Stripe test card. A webhook confirms the order and issues a QR ticket.
4. A gate staff member scans the ticket. A second scan is rejected as a duplicate.
5. The scanner goes offline, checks in another ticket, reconnects, and syncs without duplication.
6. The organizer dashboard shows sales, capacity, and check-in counts.

The demo is the acceptance test. If any step is fake — a hard-coded order, a disabled button instead of a server check, a scan that does not record a result — you have not finished. A mentor should be able to open the deployed URL, run the flow, and ask you why it works.

## What this course is not

This is not a real payment product. You will use Stripe test mode; no money moves. It is not a feature checklist. You will not build dynamic pricing, resale, transfers, or a native app. It is not a copy-paste tutorial. You get contracts, schemas, acceptance criteria, and failure tests; you write the implementation. It is not a theory course. Progress is tied to working software and evidence, not pages read.

The course also does not hide the hard parts behind a framework. You will write the inventory transaction, the webhook handler, and the scan conflict logic. That is the point. A framework can generate a CRUD screen; it cannot decide what happens when two requests claim the last seat.

## A worked example: the last ticket

Imagine ticket type `General Admission` with `capacity = 900`, `sold_quantity = 899`, and `held_quantity = 0`. The public page shows one ticket available.

Buyer A sends `POST /holds` with quantity `1` at `10:00:00.000`. Buyer B sends the same request at `10:00:00.180`. Both requests read the same state before either writes.

A naive handler does this:

```ts
const ticketType = await prisma.ticketType.findUnique({ where: { id } });
if (ticketType.capacity - ticketType.soldQuantity - ticketType.heldQuantity >= quantity) {
  await prisma.ticketType.update({
    where: { id },
    data: { heldQuantity: { increment: quantity } },
  });
}
```

Both requests can pass the check and both can increment. `held_quantity` becomes 2 for a capacity of 900, and the invariant is broken. The bug is not the `increment`; the bug is that the read and the write are separate decisions.

The correct shape is a single conditional write inside a transaction: increment only when the new total is still within capacity, and treat zero rows updated as a lost race. Module 4 makes this concrete. For now, notice the shape: **the database makes the decision, and the API translates the result into a clear response.**

The losing buyer should receive `409 CONFLICT` with a message that says the ticket is no longer available and suggests trying another tier. The winning buyer gets a hold with an expiry. Neither buyer should see a generic `500`, and neither should see a success that later disappears.

## The trade-off: depth over coverage

A commercial ticketing platform has dozens of features. A four-week course cannot teach all of them. The trade-off is deliberate: we cover one loop deeply and leave the rest as stretch work or v2.

This means some lessons will feel narrow. You will spend a chapter on hold expiry instead of adding a discount-code feature. You will test a duplicate webhook instead of building a recommendation feed. That is the point. Production engineering is mostly the discipline of making the narrow path correct under failure, not the breadth of the feature list.

The alternative — a broad course with shallow chapters — produces a portfolio that looks busy and cannot answer a single hard question. Depth is the better portfolio strategy and the better learning strategy.

## What can go wrong

The first failure is **treating the UI as the source of truth**. A disabled button, a greyed-out ticket, or a client-side countdown is not a concurrency control. The API must enforce the invariant even if the request comes from curl.

The second is **trusting the client for identity or ownership**. A request body can contain any `organizerId`, `role`, or `price`. The API must derive identity from the session and ownership from the database.

The third is **assuming a webhook arrives once**. Payment providers retry. A handler that creates an order on every delivery will duplicate tickets. The fourth is **assuming the gate has a network**. Venue wifi fails at the worst moment; the scanner needs a cached, signed ticket set and an idempotent sync path.

The fifth is **building the whole product before testing the invariant**. A beautiful event page does not matter if the last ticket can be sold twice. Build the loop, test the failure, then add polish.

## Build: write the product contract

Create `docs/product-contract.md` in your project. It should fit on one page:

1. **The promise:** one sentence describing what Ticketline does.
2. **The four invariants:** each written as a rule, with the mechanism you expect to enforce it.
3. **The demo:** the six-step flow above.
4. **The non-goals:** at least five things you will not build.
5. **The evidence:** what a mentor can inspect to prove the demo works.

Do not write code yet. This document is the contract you will test against. When a feature request appears, check it against the contract before adding it.
