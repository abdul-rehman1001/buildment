## The event ID in the URL

An organizer opens their dashboard and edits event `evt_123`. The request looks like this:

```
PATCH /api/v1/organizer/events/evt_123
```

A curious attendee changes `evt_123` to `evt_456` and sends the same request with their own valid session cookie. The API sees a signed-in user and a valid route. If the handler updates `evt_456` without checking who owns it, the attendee has just edited someone else's event.

The user was authenticated. The route was authorized by role if the route required `ORGANIZER`, but the attendee is not an organizer, so the role check would stop this particular request. Now change the attacker to a different organizer, `org_789`. They pass the role check. They send the same request for `evt_456`. The API updates an event they do not own.

That is the more dangerous case: the user has the right role, the session is valid, and the request is still wrong. The missing check is **object-level authorization**.

## Three questions, in order

Every protected request should answer three questions in this order:

1. **Who is making the request?** Resolve the session to a user. If there is no session, return `401`.
2. **Is this kind of user allowed on this route?** Check the role. If the role is wrong, return `403`.
3. **Does this user own this specific object?** Load the event, compare `organizerId` with the session user, and return `403` if they do not match. For a missing object, return `404`.

The first two checks are cheap and reusable. The third requires the object, so it belongs in the service or handler that loads it. Do not accept `organizerId`, `userId`, or `role` from the request body. The session is the only source of identity; the database is the only source of ownership.

## The four actors

Ticketline has four roles. They are global for the course, but their permissions are scoped to objects.

| Actor | Can | Cannot |
|---|---|---|
| **Attendee** | Browse published events, create holds, pay, view their own orders and tickets | Create or edit events, scan tickets, see another buyer's order |
| **Organizer** | Create and edit their own events, define ticket types, publish, view their own sales, refund their own orders | Edit another organizer's event, see platform-wide data |
| **Gate staff** | Scan tickets for assigned events, view scan results, work offline | Edit events, issue refunds, see payment details |
| **Admin** | View users and events, intervene in support cases, grant roles | Impersonate users, read raw card data |

The table is a design artifact, not documentation. It becomes a test matrix. For every endpoint, write the expected status for each actor and for the "owner vs other organizer" case. If a row is missing, the route is probably missing a check.

A permission matrix is useful because it forces you to name the object before you name the role. "Organizer" is not a permission; "the organizer who owns this event" is. "Gate staff" is not a permission; "gate staff assigned to this event" is. When you write the matrix, the object column exposes the missing check. A route that says "organizer only" but has no owner column is a route that will eventually leak.

The matrix also makes the tests cheap to design. Each cell becomes an assertion: a status code, a response code, and a database state. The negative cells are the valuable ones. A test that logs in as the owner and sees the happy path is a smoke test; a test that logs in as another organizer and asserts `403` is a security test.

The browser is outside the trust boundary. It can send any event ID, any price, any role, and any ticket code. The API validates every field and derives identity from the session. The database is the last line of defense: constraints and transactions enforce invariants even when two API requests race.

External services are not authoritative for your business rules. Stripe tells you that a payment succeeded; it does not tell you whether the buyer owns the hold or whether the order was already fulfilled. Your API decides. The email provider tells you that a message was accepted; it does not tell you that the ticket is valid.

The most common boundary mistake is to trust a value because it came from your own frontend. A request from your React app is still a request from a browser. A determined user can open the network tab, copy the request, and change every field. If the API does not re-check, the frontend is the security model — and that is not a security model.

## A worked example: the other organizer

Suppose the database contains:

```
User org_123  role ORGANIZER
User org_789  role ORGANIZER
Event evt_456 organizerId org_123
```

Organizer `org_789` sends:

```
PATCH /api/v1/organizer/events/evt_456
{ "title": "Stolen event" }
```

The handler should do this:

```ts
const event = await prisma.event.findUnique({ where: { id: req.params.id } });
if (!event) throw new HttpError(404, "Event not found.", "NOT_FOUND");
if (req.user.role !== "ADMIN" && event.organizerId !== req.user.id) {
  throw new HttpError(403, "You do not own this event.", "NOT_EVENT_OWNER");
}
// only now update
```

The order matters. If the update happens before the ownership check, the damage is done. If the check uses `req.body.organizerId`, the attacker controls the value. If the check uses the role only, both organizers pass and the event is stolen.

The error code matters too. `401` means "I do not know who you are." `403` means "I know who you are, and you may not do this." `404` means "the object does not exist." Use `404` when revealing existence would leak information, such as a private draft. For an event that is already visible in the organizer's own dashboard, `403` is clearer.

## Alternatives and trade-offs

**RBAC vs ABAC.** Role-based access control is simple: a role grants a set of route permissions. Attribute-based access control can express rules like "an organizer can edit an event only while it is a draft" or "gate staff can scan only during the event window." Ticketline starts with RBAC plus explicit ownership checks. That is enough for the core. If the rules grow, add an access policy function rather than scattering `if` statements across handlers.

**403 vs 404.** `403` is honest and easier to debug. `404` hides whether an object exists, which matters for private drafts and other tenants. Pick one policy per route and test it. Do not let different handlers choose differently by accident.

**Admin bypass.** An admin can act on any event in this course, but the bypass should be explicit and auditable. Do not write `if (user.role === "ADMIN" || event.organizerId === user.id)` in ten places; put it in one ownership function and log admin actions.

**Client-side hiding.** Hiding the edit button is a UX improvement, not an authorization control. The API must reject the request even if the button is visible. The test is a curl request with a valid session, not a click through the UI.

## What can go wrong

**IDOR.** The most common bug in multi-tenant products: an object ID from the client is trusted without an ownership check. Every route with `:id` is a candidate. Test it with two accounts.

**Confused deputy.** A gate staff member is allowed to scan "assigned events," but the handler checks only that they are gate staff. They can scan any event by changing the event ID. The assignment must be loaded and checked, not assumed from the role.

**Role from the request body.** A signup or profile update that accepts a `role` field lets the client promote itself. The role change belongs in a server-side onboarding endpoint with its own checks.

**Missing object check on list routes.** A route that lists "my events" but forgets `where: { organizerId: user.id }` returns every event. The leak is quieter than a mutation and easier to miss.

**A gate assignment that is never checked.** Gate staff can scan only assigned events. Suppose the route is `/scan/events/:eventId` and the handler checks `requireRole("GATE_STAFF")` but never loads `event_staff`. Any gate staff member can scan any event by changing the ID. The ownership object for a gate route is the assignment, not the event's organizer. The check must load the assignment and compare the event ID and the user ID before accepting a scan.

This is why the permission matrix needs an object column for every actor, not only for organizers. The attacker is not always the person with the wrong role; sometimes they are the person with the right role and the wrong object.

**Error messages that leak.** Returning "event exists but belongs to another organizer" tells an attacker the ID is real. Decide whether that is acceptable for the route. For public events, it is; for private drafts, it may not be.

## Build: write the permission matrix

Create `docs/permissions.md` in your project. For every Week 1 endpoint, fill in the expected result for each actor and for the owner-vs-other case:

| Endpoint | Attendee | Organizer (owner) | Organizer (other) | Gate staff | Admin |
|---|---|---|---|---|---|
| `GET /events` | 200 | 200 | 200 | 200 | 200 |
| `POST /organizer/events` | 403 | 201 | 201 | 403 | 201 |
| `PATCH /organizer/events/:id` | 403 | 200 | 403 | 403 | 200 |
| `POST /organizer/events/:id/publish` | 403 | 200 | 403 | 403 | 200 |
| `GET /organizer/events` | 403 | own only | own only | 403 | all |

Then implement the shared pieces:

- `requireAuth` returns `401` when there is no session.
- `requireRole(...roles)` returns `403` when the role is wrong.
- `loadOwnedEvent(user, eventId)` loads the event, returns `404` when missing, and `403` when the user is not the owner or an admin.

Acceptance criteria:

- No route accepts `organizerId` or `role` from the request body.
- Every organizer route with an event ID uses `loadOwnedEvent` or an equivalent ownership query.
- The matrix is copied into tests in Module 2.
- A curl request with another organizer's session returns `403 NOT_EVENT_OWNER`.

## Verify

Use two organizer accounts and one attendee account. For each row in the matrix, send the request and record the status. Then try the direct object attack: organizer B patches organizer A's event. The expected result is `403`, and the event must be unchanged.

Finally, check the database after the failed request. `updatedAt` should not have changed. A `403` response with a successful write is still a security failure.
