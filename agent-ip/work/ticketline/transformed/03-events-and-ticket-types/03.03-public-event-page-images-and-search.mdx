## The image in the database

A first version stores the cover image as a base64 string in the event row. The page is slow, every query drags the image, backups balloon, and the browser caches nothing useful. The database is a terrible blob store.

Ticketline stores image bytes in object storage and keeps only a key in PostgreSQL:

```
events.cover_image_key = "events/evt_123/8f3c.webp"
```

The public page resolves that key to a URL. The database stays small; the CDN does the heavy lifting. The same pattern applies to any future asset: recordings, transcripts, exports. Store the bytes in object storage; store the reference in the database.

## The upload flow

The browser should not upload through the API. A large image would occupy an API worker, consume memory, and bypass the storage service's own safeguards. Instead, the API issues a short-lived presigned URL and the browser uploads directly to storage.

The server generates the key. A client-supplied key could overwrite another event's image. The key prefix is checked before saving. A presigned PUT does not enforce a maximum file size; for a production cap, use a presigned POST policy or a storage rule. The course states this limitation rather than pretending the upload is fully constrained.

## Storage configuration

```ts
import { S3Client } from "@aws-sdk/client-s3";
import { env } from "./config.js";

export const s3 = new S3Client({
  region: env.S3_REGION,
  endpoint: env.S3_ENDPOINT,
  forcePathStyle: true, // required for MinIO
  credentials: {
    accessKeyId: env.S3_ACCESS_KEY,
    secretAccessKey: env.S3_SECRET_KEY,
  },
});
```

Add `S3_PUBLIC_URL` to the environment. Locally it points at MinIO; in production it points at a CDN or a public bucket URL. Do not put the bucket credentials in the browser. The presigned URL is the only temporary credential the browser needs.

## The public page

The public page has one job: help a buyer decide whether to attend and what to buy. It should show:

- the event title, cover, description, venue, and local start time;
- the ticket types, prices, availability, and sold-out state;
- a clear primary action (in Week 2, "Choose tickets"; in Week 1, the ticket list);
- an empty or error state that does not pretend the event exists.

```tsx
const starts = new Intl.DateTimeFormat("en-US", {
  dateStyle: "full",
  timeStyle: "short",
  timeZone: event.timezone,
}).format(new Date(event.startsAt));
```

Accessibility and mobile checks:

- The cover has descriptive alt text.
- The heading order is `h1` then `h2`.
- The ticket rows are readable at a narrow width.
- Sold-out is text, not only a color.
- The page does not require hover to read the price.
- The primary action is reachable by keyboard.

A public page that shows a stale or impossible state is worse than a plain page. The availability number must come from the server projection, not a client-side counter. In Week 2, the hold flow makes that number change; the page should show "checking availability" while a request is in flight rather than guessing.

Image optimization is part of the page's performance budget. A 4 MB phone photo on a 360px card wastes bandwidth and slows the catalogue. Resize or transform the image before upload, or use an image service that does it on delivery. Prefer WebP or AVIF with a JPEG fallback. Set explicit width and height so the page does not shift while the image loads. A cover that causes layout shift makes the page feel broken even when the data is correct.

Alt text is part of the content, not a compliance checkbox. "Event cover" is useless. "Crowd under warm string lights at the riverside stage" tells a screen-reader user what the image contributes. If the cover is decorative, say so and hide it; if it carries meaning, describe the meaning. The organizer can write the alt text in the event form, and the API should store it with the cover key.

Responsive images matter more for the catalogue than the detail page. The catalogue may show 12 covers at once; a single oversized image can dominate the page load. Use a smaller variant for cards and a larger variant for the detail page. The storage key can remain the same; the delivery URL can include a width parameter if your image service supports it. If you serve the original everywhere, measure the page weight before calling it done.

## The catalogue

The public list starts from the public state:

```ts
const where = {
  status: "PUBLISHED" as const,
  ...(query.from || query.to
    ? { startsAt: { ...(query.from ? { gte: query.from } : {}), ...(query.to ? { lte: query.to } : {}) } }
    : {}),
  ...(query.q
    ? {
        OR: [
          { title: { contains: query.q, mode: "insensitive" as const } },
          { venueName: { contains: query.q, mode: "insensitive" as const } },
        ],
      }
    : {}),
};
```

The route returns a predictable envelope:

```json
{
  "items": [],
  "page": 1,
  "limit": 12,
  "total": 0,
  "totalPages": 0
}
```

The `limit` is capped at 50 so a client cannot ask for 10,000 rows in one request.

## Index reality

`@@index([status, startsAt])` helps the published-and-date filter. A `contains` search with a leading wildcard (`%ticket%`) does not use a normal B-tree index. At the course's scale, that is fine. At real scale, use one of:

- PostgreSQL full-text search (`tsvector`, `GIN`);
- trigram indexes (`pg_trgm`);
- an external search service.

Do not claim the contains query is indexed when it is not. Write the limitation in `docs/decisions.md` and revisit it if the catalogue grows. A query plan (`EXPLAIN ANALYZE`) is the evidence; "it feels fast" is not.

Search UX is part of the same contract. A search box that sends a request on every keystroke can produce a request storm and out-of-order responses. Debounce the input, cancel the previous request, and show the query that produced the results. If the user types "live" and then "live music", the page should not render the result for "live" after the result for "live music". A simple request ID or an AbortController solves the ordering problem.

The empty state should suggest the next action: clear the query, widen the date range, or browse all events. An empty page with no explanation looks like a bug. The result count and the active filters should be visible, so the user knows why a result is missing. If a filter excludes drafts, do not mention drafts; the user should not learn about internal states from the public UI.

Pagination is a product decision. Offset pagination is simple and fine for a small catalogue. It can skip or duplicate rows when events are inserted between pages; that is acceptable at this scale. Cursor pagination is better for a busy feed, but it adds a cursor contract and a stable sort. Do not add it until the catalogue size or the ordering bug justifies it.

## Alternatives and trade-offs

**Presigned upload vs API proxy.** A proxy is simpler to reason about and can enforce size limits, but it spends API bandwidth and memory. Presigned uploads are the production default for object storage. Use the proxy only for small files or when you need server-side transformation.

**S3 vs Cloudinary.** S3 gives you control and a low storage cost; you own resizing and CDN setup. Cloudinary gives you transformations and a simpler upload API, at a vendor cost. The course uses S3-compatible storage because the same pattern works with R2, S3, and MinIO.

**Postgres search vs a search service.** Postgres full-text or trigram indexes are enough for a small catalogue. A dedicated search service adds relevance tuning, faceting, and operational cost. Do not add it before you have a query that needs it.

**Server-rendered page vs client-side fetch.** A server-rendered page is faster on first load and better for SEO. A client-side page is easier to make interactive. Start server-rendered; add client interactivity only for the parts that need it.

## What can go wrong

**Base64 images in the database.** The row becomes huge and every query pays for it. Store the key.

**Client-supplied object keys.** A client can overwrite another event's image. Generate the key on the server and check the prefix.

**Unvalidated content types.** An uploaded HTML or SVG can become an XSS vector if served inline. Allow only image types and serve with the correct content type; sanitize SVG if you allow it.

**No size cap.** A presigned PUT can accept a huge file. Add a POST policy or a storage rule for production.

**Expired presigned URLs.** Five minutes is enough for a small cover; a slow connection may need more. Make the expiry explicit and show a retry path.

**Stale availability.** The public page reads a snapshot. Do not treat it as a reservation; the hold endpoint decides.

**Search that leaks drafts.** The catalogue must start from `status = PUBLISHED`. A search filter is not a visibility rule.

**Unindexed search claims.** A leading-wildcard `contains` scans. Document the limitation and measure before optimizing.

**Inaccessible images.** A cover without alt text fails the public page. Describe the event, not the file.

## Build

1. Add the S3 client and `S3_PUBLIC_URL`.
2. Add the presign route with content-type validation and a server-generated key.
3. Add a route to save the cover key, with a prefix check.
4. Upload a test image to MinIO and verify it appears.
5. Build the public event page with the event time in its zone.
6. Add the catalogue route with published-only filtering, search, date filters, and pagination.
7. Add the catalogue page with an empty state and a search input.
8. Add tests for published-only visibility, search, pagination, and the limit cap.

Acceptance criteria:

- An image upload returns a presigned URL and a server-generated key.
- Uploading with `image/gif` returns `400`.
- The saved key belongs to the event's prefix.
- The public page shows the cover, title, local time, venue, description, and ticket types.
- A draft event's slug returns `404`.
- The page is readable at 375px width and with keyboard navigation.
- The catalogue never returns a draft or cancelled event.
- `?limit=1000` is rejected or capped at 50.

## Verify

```bash
curl -X POST http://localhost:4000/api/v1/organizer/events/$EVENT_ID/cover-upload \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"contentType":"image/webp"}'
```

Use the returned `uploadUrl` with `curl -X PUT --data-binary @cover.webp`. Then save the key and open the public page. The image should load from `S3_PUBLIC_URL`.

For search, create a draft and a published event, then call `GET /events?q=...`. Only the published event should appear. Add a second page and assert the pagination envelope.
