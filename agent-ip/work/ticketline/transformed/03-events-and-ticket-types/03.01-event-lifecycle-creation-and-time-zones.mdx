## The draft that leaked

An organizer creates an event but has not finished the description, venue, or ticket types. The public catalogue query filters by a boolean `isPublished`, but a direct URL `/events/my-draft` still renders the event because the detail route only checks that the row exists.

The bug is not the missing filter in one query. The bug is that the event has no explicit state machine. `isPublished` cannot express "cancelled" or "completed", and every new query has to remember the boolean rule.

The second bug in the same product is the event time. An organizer in New York creates an event for 7:00 p.m. on March 8, 2026. The form sends `2026-03-08T19:00:00` with no zone. The server stores it as UTC. The public page renders 3:00 p.m. New York time. The venue opens at 7:00 p.m.; attendees arrive at 3:00 p.m.

Both bugs come from the same root: the product does not model states or time explicitly. The database stores a boolean and a naked timestamp, and every handler has to remember the missing context.

## Four states

| State | Meaning | Public? | Allowed next states |
|---|---|---|---|
| `DRAFT` | The organizer is still editing | No | `PUBLISHED`, `CANCELLED` |
| `PUBLISHED` | On sale and visible | Yes | `CANCELLED`, `COMPLETED` |
| `CANCELLED` | Called off; refunds may be in progress | No | none |
| `COMPLETED` | The event has happened | Yes, as an archive | none |

Cancelled and completed are terminal. If an organizer wants to run the event again, they create a new event rather than resurrecting history. That keeps orders, tickets, and scans attached to the event they belonged to.

The state machine is small on purpose. A complex approval workflow, a suspended state, or a resale window would add states and transitions that the core loop does not need. Add a state only when a real business rule requires it.

## The transition guard

Create `apps/api/src/events/lifecycle.ts`:

```ts
import type { EventStatus } from "../generated/prisma/index.js";
import { HttpError } from "../errors.js";

const transitions: Record<EventStatus, EventStatus[]> = {
  DRAFT: ["PUBLISHED", "CANCELLED"],
  PUBLISHED: ["CANCELLED", "COMPLETED"],
  CANCELLED: [],
  COMPLETED: [],
};

export function assertEventTransition(from: EventStatus, to: EventStatus) {
  if (!transitions[from].includes(to)) {
    throw new HttpError(
      409,
      `An event cannot move from ${from} to ${to}.`,
      "INVALID_EVENT_TRANSITION"
    );
  }
}
```

The guard is a pure function, so it is cheap to unit test. The route calls it before the update. The database enum guarantees the vocabulary; the guard guarantees the allowed moves.

## Publish is more than a status change

A publish request must prove the event is ready:

1. At least one ticket type exists.
2. Every ticket type has a positive capacity.
3. The event has a title, venue, start, and end.
4. The sale window is valid and not entirely in the past.
5. The organizer owns the event.

If a condition fails, return `422` with a specific reason, not a generic `400`. The organizer needs to know what to fix.

```ts
export function assertEventReady(event: {
  title: string;
  venueName: string;
  startsAt: Date;
  endsAt: Date;
  salesStartAt: Date;
  salesEndAt: Date;
  ticketTypes: { capacity: number }[];
}) {
  const problems: string[] = [];
  if (!event.title.trim()) problems.push("Add a title.");
  if (!event.venueName.trim()) problems.push("Add a venue.");
  if (event.endsAt <= event.startsAt) problems.push("The event must end after it starts.");
  if (event.salesEndAt <= event.salesStartAt) problems.push("The sale window is invalid.");
  if (event.ticketTypes.length === 0) problems.push("Add at least one ticket type.");
  if (event.ticketTypes.some((t) => t.capacity <= 0)) problems.push("Every ticket type needs capacity.");
  if (problems.length) {
    throw new HttpError(422, problems[0], "EVENT_NOT_READY");
  }
}
```

The check runs before the transition. A `DRAFT` event with no tickets stays a draft and gets a useful error. A `CANCELLED` event cannot be published at all; the transition guard returns `409`.

## Time zones

Store two things:

- The instant, as UTC (`startsAt`, `endsAt`, `salesStartAt`, `salesEndAt`).
- The event's IANA zone (`America/New_York`, `Europe/London`).

The form sends ISO instants with an explicit offset or `Z`, plus the IANA zone. The API validates the zone with `Intl.DateTimeFormat`:

```ts
const isValidTimeZone = (value: string) => {
  try {
    new Intl.DateTimeFormat(undefined, { timeZone: value });
    return true;
  } catch {
    return false;
  }
};
```

The public page formats the UTC instant with the event zone:

```ts
new Intl.DateTimeFormat("en-US", {
  dateStyle: "full",
  timeStyle: "short",
  timeZone: event.timezone,
}).format(new Date(event.startsAt));
```

An offset alone is not enough. `-05:00` is correct in winter and wrong in summer for New York. The named zone carries the daylight-saving rules. A test should format a winter date and a summer date and assert different offsets.

A worked example makes the bug concrete. Suppose the organizer picks 7:00 p.m. on March 8, 2026 in `America/New_York`. The correct UTC instant is `2026-03-08T23:00:00Z`, because daylight saving starts that morning. If the form sends `2026-03-08T19:00:00` and the server treats it as UTC, the public page formats the event as 3:00 p.m. New York time. The organizer, the venue, and the buyer all disagree about the start time. A fixed `-05:00` offset produces the same error after the transition.

The fix is to capture the event zone at authoring time and to send an absolute instant. Do not infer the zone from the server's locale; the server may run in UTC, and the organizer may be traveling. Do not infer it from the browser's current zone either; the event can be in a different city. The organizer chooses the event zone explicitly.

## Slugs

A slug is a human-readable URL key. It must be unique and stable enough to share.

```ts
export function slugify(title: string) {
  const base = title
    .toLowerCase()
    .trim()
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "")
    .slice(0, 48);

  return `${base || "event"}-${randomBytes(3).toString("hex")}`;
}
```

Do not use the title alone. Two organizers can run "Summer Live" on the same night. The random suffix keeps the slug unique without a database round trip; the unique constraint is the final guard. Do not regenerate the slug on every edit; old links should keep working.

## Create and edit

`POST /organizer/events` creates a draft:

```ts
organizerEventRouter.post("/events", async (req, res, next) => {
  try {
    const input = eventInputSchema.parse(req.body);
    const event = await prisma.event.create({
      data: {
        ...input,
        organizerId: req.user!.id,
        slug: slugify(input.title),
      },
    });
    res.status(201).json({ success: true, data: event });
  } catch (error) {
    next(error);
  }
});
```

`organizerId` comes from the session. If the request body contains an `organizerId`, Zod strips it because the schema does not include it. Do not spread untrusted input into the create data.

`PATCH /organizer/events/:id` loads the event, checks ownership, validates the partial input, and updates. If the event is published and has orders, editing the date or venue may require a warning or a new version. Ticketline v1 allows the edit but records `updatedAt`; Week 4 discusses the gap. Do not silently change the price of an existing ticket type; the price snapshot arrives in Module 5.

Editing a published event is a product decision disguised as a form. A typo in the description is safe to fix. A change to the start time can strand buyers who planned around the old time. A change to the venue can invalidate directions, parking, and accessibility information. A change to the sale window can close sales early or reopen a sold-out event. The API cannot know which edits are safe for every organizer, so it should warn when the event is published and has enrollments or orders, and record the change. A full versioned-release model is v2; the warning and the audit trail are the v1 compromise.

The same caution applies to cancellation. Cancelling an event is not a status flip; it starts refunds, notifications, and access-control changes. In Week 1, cancellation only changes the public visibility and the allowed transitions. In Week 2, it must interact with holds and orders. Do not build a cancellation flow that assumes the event has no money attached to it.

## Public visibility

The public detail query starts from the public state:

```ts
const event = await prisma.event.findFirst({
  where: { slug: req.params.slug, status: "PUBLISHED" },
  include: { ticketTypes: true },
});
```

The `status` filter is part of the query, not a UI check. A direct URL to a draft returns `404`. The organizer can still view their own draft through an organizer route that loads by ID and checks ownership.

## What can go wrong

**Boolean publish state.** `isPublished` cannot express cancelled or completed. Use an enum and a transition guard.

**Publishing an empty event.** An event with no ticket types cannot be sold. Return `422` with the specific missing condition.

**Direct URL leakage.** The public detail route must filter by status. A list filter is not enough.

**Time-zone bugs.** A naked local timestamp is stored as UTC. Send ISO instants with an offset plus the IANA zone, and test DST.

**Slug collisions.** Two events with the same title overwrite each other. Use a random suffix and a unique constraint.

**Editing a published event.** A date change after tickets are sold can confuse buyers. Warn the organizer and record the change; versioned releases are a v2 feature.

**Invalid sale windows.** Sales that end after the event starts, or before they begin, create a confusing page. Validate the relationship between the event and sale windows.

**Cancelled events in the catalogue.** The public query must exclude `CANCELLED` as well as `DRAFT`. A simple `status !== DRAFT` is not enough.

**Publishing before the sale window.** An event can be published with a sale window that starts next month. That is valid: the page is visible, the tickets are not yet on sale. The page should show "sales open on…" rather than a broken buy button. Do not reject a future sale window just because it is not active yet; validate the order of the dates, not whether they are currently open.

**Publishing after the event ended.** An event whose end time is in the past should not be published as a live product. The readiness check should reject it with a clear message. A completed archive is a different state; do not let a new draft masquerade as a live event.

## Build

1. Add the lifecycle module and the transition guard.
2. Add the shared event schema with the time-zone validation.
3. Implement create, edit, list-own, publish, and cancel routes.
4. Filter every public query to `status: "PUBLISHED"`.
5. Build the organizer form with an IANA zone selector and ISO instants.
6. Add the public event page shell; the full page arrives in 3.3.

Acceptance criteria:

- Draft → published succeeds when the event is ready.
- Draft → published fails with `422` when there are no ticket types.
- Published → cancelled succeeds.
- Cancelled → published returns `409 INVALID_EVENT_TRANSITION`.
- A direct request to a draft event's public route returns `404`.
- The organizer can still view their own draft.
- The public page shows the correct local time for a winter and a summer date.

## Verify

```bash
curl -X POST http://localhost:4000/api/v1/organizer/events \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title":"Last Ticket","timezone":"America/New_York","startsAt":"2026-03-08T23:00:00Z",...}'
```

Then publish with no ticket types and expect `422 EVENT_NOT_READY`. Publish after adding a ticket type and expect `200`. Cancel and try to republish; expect `409`.

A unit test for the time zone:

```ts
const instant = new Date("2026-03-08T23:00:00.000Z"); // 7:00 p.m. EDT
const formatted = new Intl.DateTimeFormat("en-US", {
  timeZone: "America/New_York",
  hour: "numeric",
  minute: "2-digit",
}).format(instant);
expect(formatted).toBe("7:00 PM");
```
