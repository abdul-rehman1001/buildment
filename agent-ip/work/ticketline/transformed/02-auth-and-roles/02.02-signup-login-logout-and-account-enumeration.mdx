## The login route that leaks accounts

A login endpoint returns `404 User not found` for an unknown email and `401 Wrong password` for a known email with a bad password. An attacker now has an account-enumeration oracle: they can test email addresses until they find valid accounts, then focus the password attack.

The fix is not a better error message. The fix is to return the same response for both cases and to spend roughly the same time on both paths. That is harder than it sounds, because a database lookup, a password hash, and an early return all take different amounts of time.

This chapter builds the four auth endpoints — signup, login, logout, and me — with those failure modes in mind. The goal is not a perfect auth system. The goal is a small system whose failure behavior you can explain and test.

## Validation and normalization

Create shared schemas so the API and web app agree:

```ts
import { z } from "zod";

export const signupSchema = z.object({
  email: z.string().trim().toLowerCase().email(),
  name: z.string().trim().min(2).max(80),
  password: z.string().min(12).max(200),
});

export const loginSchema = z.object({
  email: z.string().trim().toLowerCase().email(),
  password: z.string().min(1).max(200),
});
```

Email normalization matters. `Ada@Example.com` and `ada@example.com` should be the same account. Trim whitespace before validating. The password minimum is 12 characters for this course; length is a better lever than arbitrary character-class rules. A breached-password check is a good Week 4 addition. Do not reject a password because it lacks a symbol; that rule pushes users toward predictable patterns.

The API re-validates every field. The web form can show a friendly error, but the server is the boundary. A malformed request should return `400` with a field-specific error, not a stack trace.

## Signup

Signup creates the user and a session. It must handle the existing-email case deliberately. The course returns `409 EMAIL_IN_USE`, because the signup form needs to tell the user why it failed. This does reveal that an account exists. That is a trade-off: signup UX is more important here than hiding account existence. Login has the opposite trade-off.

```ts
authRouter.post("/signup", async (req, res, next) => {
  try {
    const input = signupSchema.parse(req.body);

    const existing = await prisma.user.findUnique({ where: { email: input.email } });
    if (existing) {
      return res.status(409).json({
        success: false,
        message: "An account with that email already exists.",
        code: "EMAIL_IN_USE",
      });
    }

    const user = await prisma.user.create({
      data: {
        email: input.email,
        name: input.name,
        passwordHash: await hashPassword(input.password),
      },
    });

    const session = await createSession(user.id);
    setSessionCookie(res, session.token);

    res.status(201).json({
      success: true,
      data: { id: user.id, email: user.email, name: user.name, role: user.role },
    });
  } catch (error) {
    next(error);
  }
});
```

The role is not accepted from the body. Every signup creates an `ATTENDEE`. Becoming an organizer is a separate, verified flow in 2.4.

## Login and enumeration

The login response must be identical for "unknown email" and "wrong password." The status is `401`, the message is `Invalid email or password.`, and the code is `INVALID_CREDENTIALS`.

```ts
authRouter.post("/login", async (req, res, next) => {
  try {
    const input = loginSchema.parse(req.body);
    const user = await prisma.user.findUnique({ where: { email: input.email } });

    // Always verify something so timing does not reveal whether the email exists.
    const hash = user?.passwordHash ?? DUMMY_ARGON2_HASH;
    const valid = await verifyPassword(hash, input.password).catch(() => false);

    if (!user || !valid) {
      return res.status(401).json({
        success: false,
        message: "Invalid email or password.",
        code: "INVALID_CREDENTIALS",
      });
    }

    const session = await createSession(user.id);
    setSessionCookie(res, session.token);

    res.json({
      success: true,
      data: { id: user.id, email: user.email, name: user.name, role: user.role },
    });
  } catch (error) {
    next(error);
  }
});
```

`DUMMY_ARGON2_HASH` must be a real hash produced by the same Argon2 parameters, not a made-up string. If the hash is malformed, `verifyPassword` throws immediately and the timing difference returns. Generate the dummy hash once at boot and reuse it.

The timing is still not perfectly equal. The database lookup for an existing user and the session insert for a successful login add work. The goal is to remove the obvious early return, not to build a constant-time login. A rate limiter is the stronger control.

The error envelope is part of the contract. Every failure returns `success: false`, a human-readable `message`, and a stable `code`. The code is what clients branch on; the message is what humans read. Do not make the client parse English. Do not return a raw Prisma error, a stack trace, or a validation library dump. A learner who sees `P2002` in the UI has been failed by the API.

The client should handle the same four cases for every auth call: success, invalid input, invalid credentials, and rate limit. A `401` should return the user to the form with a neutral message; a `409` on signup should suggest signing in; a `429` should show a retry time. A generic "something went wrong" for all of them hides the one piece of information the user needs.

## Rate limits

Login and signup are credential endpoints; there is no authenticated user yet. Limit by IP and by email:

```ts
const loginLimiter = rateLimit({
  windowMs: 60_000,
  limit: 10,
  standardHeaders: "draft-7",
  legacyHeaders: false,
  keyGenerator: (req) => `${req.ip}:${String(req.body?.email ?? "")}`,
});
```

Apply a tight per-email limit and a looser per-IP limit. A shared office or campus IP can produce many legitimate attempts; a single email with 50 attempts per minute is a credential-stuffing signal. Do not rely on the client to throttle.

The limiter is in-memory in the course. That is per process and resets on restart. For a single API process it is enough. If you scale horizontally, move the counter to Redis or use a gateway. Document the limitation.

## Logout and me

Logout deletes the session row and clears the cookie:

```ts
authRouter.post("/logout", authenticate, async (req, res) => {
  if (req.sessionId) await revokeSession(req.sessionId);
  clearSessionCookie(res);
  res.status(204).end();
});
```

`/me` requires authentication:

```ts
authRouter.get("/me", authenticate, (req, res) => {
  if (!req.user) {
    return res.status(401).json({
      success: false,
      message: "Not signed in.",
      code: "AUTH_REQUIRED",
    });
  }

  res.json({
    success: true,
    data: {
      id: req.user.id,
      email: req.user.email,
      name: req.user.name,
      role: req.user.role,
      emailVerified: Boolean(req.user.emailVerifiedAt),
    },
  });
});
```

Logout returns `204` even if there was no session. The client clears its local state either way. Do not return an error that lets a user think they are still signed in.

## CSRF and the cookie model

`SameSite=Lax` blocks most cross-site form POSTs, but it is not a complete CSRF defense. The course uses a same-origin proxy, so the cookie is sent only to the app's own origin. If you deploy the API on a different domain, you need `SameSite=None; Secure` and a CSRF token for state-changing requests.

A simple CSRF defense for the course: require a custom header such as `X-Requested-With: ticketline` on state-changing requests from the web app. A cross-site form cannot set that header. This is not a substitute for a proper token, but it raises the bar and is easy to test. Week 4 revisits the production policy.

## A worked example: wrong password vs unknown email

Request A:

```http
POST /api/v1/auth/login
{ "email": "known@example.test", "password": "wrong" }
```

Request B:

```http
POST /api/v1/auth/login
{ "email": "missing@example.test", "password": "wrong" }
```

Both responses:

```http
HTTP/1.1 401 Unauthorized
{ "success": false, "message": "Invalid email or password.", "code": "INVALID_CREDENTIALS" }
```

The bodies and statuses match. The timing should be comparable because both paths perform one Argon2 verification. A test can assert the status and body; timing tests are flaky, so measure manually and document the dummy-hash approach.

## Alternatives and trade-offs

**Magic links.** No password to hash or leak. The email deliverability and link expiry become the critical path. It is a good alternative for consumer products, but it hides the password-hashing lesson the course wants to teach.

**OAuth / social login.** Moves credential handling to a provider. It adds redirect URIs, state parameters, and account linking. It is a good Week 4 stretch, not the core.

**Passkeys / WebAuthn.** Strong phishing resistance and no shared secret. The browser and server flow is more complex, and the course would spend its time on WebAuthn instead of sessions and authorization. Keep it as a stretch.

**JWT.** Discussed in 2.1. It makes logout and revocation harder for this product. If you use it, add a denylist and test it.

## What can go wrong

**Enumeration through error text.** Different messages for unknown email and wrong password leak accounts. Use one message.

**Enumeration through timing.** An early return for unknown email is measurably faster. Use a dummy hash.

**Credential stuffing.** Attackers reuse breached passwords. Rate limits, breached-password checks, and eventually MFA are the defenses. The course adds rate limits now and discusses the rest in Week 4.

**Password in logs.** A request logger that prints the body leaks credentials. Redact `password` fields.

**Cookie not cleared on logout.** The row is deleted but the browser keeps the cookie; the next request fails, which is correct, but the UI may show a stale signed-in state. Clear the cookie and the client state.

**Session fixation.** Do not accept a session token from the request body. Create a new token on login.

**Wrong status codes.** `200` with `{ success: false }` for a failed login is confusing and can break clients. Use `401` for bad credentials, `409` for an existing email, `400` for invalid input, `429` for rate limits.

## Build

1. Create `apps/api/src/auth/schemas.ts` with the signup and login schemas.
2. Create `apps/api/src/auth/password.ts`, `session.ts`, `cookie.ts`, and `create-session.ts`.
3. Create `apps/api/src/auth/routes.ts` with signup, login, logout, and me.
4. Mount the router at `/api/v1/auth`.
5. Add the login and signup rate limiters.
6. Add the web forms for signup and login, using the shared schemas.
7. Add a `/me` fetch on the signed-in shell.

Acceptance criteria:

- Signup returns `201` and sets an HttpOnly cookie.
- Login returns `401` with the same body for unknown email and wrong password.
- `/me` without a cookie returns `401`.
- `/me` with a cookie returns the user.
- Logout returns `204`; the old cookie no longer works.
- A password is never returned in a response or written to a log.

## Verify

```bash
curl -i -X POST http://localhost:4000/api/v1/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"organizer@example.test","name":"Ada","password":"correct horse battery staple"}'

curl -i -X POST http://localhost:4000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"organizer@example.test","password":"wrong-password"}'

curl -i http://localhost:4000/api/v1/auth/me
```

Then use a cookie jar to log in, call `/me`, log out, and call `/me` again. The last call must be `401`.
