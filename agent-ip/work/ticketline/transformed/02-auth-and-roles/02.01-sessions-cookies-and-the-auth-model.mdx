## The employee who still has a key

An organizer is removed from the platform at 09:00. Their browser still holds an access token that expires at 09:15. For fifteen minutes, the removed account can still create events. If the same account also holds a refresh token, the window can be much longer.

You can add a denylist, shorten the token lifetime, or rotate keys. Or you can use a session that the server can delete immediately. The choice is not about which token is more modern. It is about which failure you can tolerate.

Ticketline uses a server-side session because the product needs immediate revocation, simple reasoning, and a logout that actually logs out. The cost is one session lookup per authenticated request. At this scale, that lookup is cheap.

## Opaque sessions vs JWTs

| Property | Opaque session (Ticketline) | JWT |
|---|---|---|
| What the token contains | A random string; no user data | Signed claims: user id, role, expiry |
| Server storage | One row per session | No server row (unless denylist) |
| Verification | Hash the token and look up the row | Verify the signature |
| Revocation | Delete the row; immediate | Denylist, short expiry, or key rotation |
| Stateless scaling | Needs a shared session store or sticky sessions | Easy across services |
| Failure if the database is down | Authenticated requests fail closed | Requests can continue with a valid signature |
| Best fit | First-party web app with logout and role changes | Stateless APIs and cross-domain services |

The table is the trade-off. Sessions are not "better" in every dimension. They are better for an app where a removed organizer must lose access immediately and where the database is already on the request path.

A JWT with a five-minute expiry and a denylist can approximate the same behavior. It adds a cache, a key rotation plan, and a clock-skew story. You can build that; Ticketline does not need it.

## The session lifecycle

The lifecycle is intentionally small. A session is created on login, used on every request, and ends by expiry or revocation. There is no sliding refresh token and no device list in v1. Those are useful additions, but they add moving parts that the core loop does not need.

Expiry and revocation are different. Expiry is a timestamp; the row may still exist after it passes. Revocation is a delete. The authenticate middleware checks the timestamp and deletes an expired row when it sees one. Logout deletes the row immediately and clears the cookie.

## How the token flows

1. Login verifies the password.
2. The API creates a random token with `crypto.randomBytes(32)`.
3. The API stores `sha256(token)` in `sessions.token_hash`.
4. The API sends the raw token in an HttpOnly cookie.
5. The browser sends the cookie on every same-origin request.
6. The API hashes the cookie value and looks up the session.
7. If the session is missing or expired, the request is unauthenticated.

The raw token never appears in the database, logs, or URL. The hash is enough to find the session and useless if leaked. This is the same reasoning as password hashing: the server should not store a credential it does not need to replay.

## Cookie flags

| Flag | Value | Why |
|---|---|---|
| `HttpOnly` | true | JavaScript cannot read the cookie |
| `Secure` | true in production | The cookie is only sent over HTTPS |
| `SameSite` | `Lax` | Blocks most cross-site POSTs while allowing normal navigation |
| `Path` | `/` | The cookie is sent to the app |
| `Max-Age` | 30 days | The session expires even if the user never logs out |

`SameSite=Lax` is not a complete CSRF defense. In a cross-origin deployment you may need `SameSite=None; Secure` plus a CSRF token. Ticketline uses a same-origin proxy in development, so `Lax` is the right default here. The production cookie policy depends on the deployment; Week 4 revisits it.

Do not store the session token in `localStorage`. It is readable by any script on the page, and it does not get the `HttpOnly` protection. The cookie is the delivery mechanism; the server is the authority.

The cookie flags protect the token in transit and from script access, but they do not make the session magically safe. An attacker with access to the browser profile can still use the cookie. A shared computer with a logged-in session is a real risk. That is why logout must revoke the server row and why the session should have an expiry even if the user never clicks logout.

The cookie also does not tell you whether the user is still allowed to do something. The role is read from the user row on each request. If an admin demotes an organizer, the session remains valid, but the role check fails on the next request. That is the desired behavior: the session proves identity; the database proves current permission. Do not cache the role in the cookie or the token unless you also invalidate the session when the role changes.

## A worked example: the second request

Suppose the login response sets:

```
Set-Cookie: tl_session=8f3c...; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000
```

The database row is:

```
sessions.id = sess_1
sessions.token_hash = sha256("8f3c...")
sessions.user_id = user_42
sessions.expires_at = 2026-11-19T10:00:00Z
```

The next request carries `Cookie: tl_session=8f3c...`. The API hashes the value, finds `sess_1`, checks the expiry, and attaches `user_42` to the request. If the row is missing, the request continues unauthenticated; `requireAuth` returns `401`.

If the user logs out, the API deletes `sess_1` and sends `Set-Cookie: tl_session=; Max-Age=0`. The next request has no valid row. A copied cookie from before logout also fails because the row is gone.

## Alternatives and trade-offs

**JWT with short expiry.** Good for stateless services. For Ticketline, it makes logout and role changes eventual rather than immediate. If you choose it, add a denylist and a key rotation plan, and test revocation.

**Refresh tokens.** Useful for long-lived mobile clients. They add a second token, rotation, reuse detection, and a revocation store. Ticketline's web session already lasts 30 days; a refresh token is unnecessary for the course.

**Magic links or passkeys.** A good UX alternative to passwords. The course uses passwords because they make hashing, timing, and login enumeration visible. A magic-link-only course would hide those lessons. You can add passkeys as a stretch.

**Server-side sessions with Redis.** A shared Redis session store lets multiple API instances share sessions without a database lookup on every request. It adds a dependency and a cache-invalidation story. Postgres is enough for the course.

## What can go wrong

**Session fixation.** The API must create a new session token on login, not reuse a token supplied by the client. Never accept a session ID from the request body.

**Token leakage in logs.** Request loggers that print cookies or authorization headers leak credentials. Redact them. The course's logger should not print the raw cookie.

**Logout that only clears the cookie.** The row remains valid; a copied token still works. Delete the row.

**Expired sessions that are never cleaned.** Checking `expires_at` is enough for security, but the table grows. Delete expired rows on access or with a job.

**Cookie misconfiguration.** `Secure` in local HTTP prevents the cookie from being sent. `SameSite=None` without `Secure` is rejected by browsers. Match the cookie policy to the environment.

**Role changes that do not invalidate the session.** If a user's role changes, the session row still points to the user; the role is read from the user row. That is fine. If you cache the role in a token, it can go stale. Ticketline reads the role from the database on each request.

**Session cleanup grows into a table scan.** Checking `expires_at` on each request is enough for security, but the table accumulates dead rows. Delete expired rows when they are encountered, and add a periodic cleanup job for the rest. A partial index on `expires_at` can make the cleanup cheap.

**Rotation after a privilege change.** When a user becomes an organizer, you can keep the existing session because the role is read from the user row. When a password changes or a compromise is suspected, revoke all sessions for that user. `revokeAllSessions(userId)` is the small tool that makes the second case possible. Without it, the user has to wait for every session to expire.

A session test should cover the three states, not only the happy path. Create a session, call an authenticated route with the cookie, and assert the user. Insert an expired session and assert `401` plus deletion. Delete the session and replay the cookie; assert `401`. Finally, create two sessions for the same user and assert that revoking one does not revoke the other. That last test catches a `deleteMany({ userId })` written where a single-row delete was intended, which would log the user out of every device when they log out of one.

## Build

Create `apps/api/src/auth/session.ts`, `cookie.ts`, `authenticate.ts`, and `create-session.ts`. The interfaces are:

```ts
export function createSessionToken(): string;
export function hashSessionToken(token: string): string;
export function sessionExpiry(now?: number): Date;
export function setSessionCookie(res: Response, token: string): void;
export function clearSessionCookie(res: Response): void;
export async function createSession(userId: string): Promise<{ token: string; expiresAt: Date }>;
export async function revokeSession(sessionId: string): Promise<void>;
export const authenticate: RequestHandler;
```

Acceptance criteria:

- A raw session token is never stored in the database.
- An expired session is rejected and deleted.
- Logout deletes the session row.
- The cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in production.
- `authenticate` attaches the user when a valid session exists and does not reject missing sessions.

## Verify

Use `node:crypto` in a unit test:

```ts
expect(hashSessionToken("abc")).not.toBe("abc");
expect(hashSessionToken("abc")).toBe(hashSessionToken("abc"));
```

Create two sessions for the same user and assert the hashes differ. Insert an expired session and call `/me` with its cookie; expect `401` and assert the row is gone. Log out and replay the old cookie; expect `401`.
