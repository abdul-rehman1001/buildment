## The route that trusted the role

An organizer route is protected with `requireRole("ORGANIZER")`. Organizer B sends a request for Organizer A's event. The role check passes; the event ID is accepted; the update succeeds. The API was authenticated and role-authorized, but not object-authorized.

This is the same IDOR failure from 1.2, now in code. The fix is a second check after the object is loaded. The chapter builds that check once and makes every organizer route use it.

## Three checks, in order

Every protected request should answer three questions:

1. **Who is making the request?** Resolve the session to a user. No session → `401`.
2. **Is this kind of user allowed on this route?** Check the role. Wrong role → `403`.
3. **Does this user own this specific object?** Load the object, compare ownership, and return `403` or `404` when it does not match.

The first two checks are reusable middleware. The third requires the object, so it belongs in the service or handler that loads it. Do not accept `organizerId`, `userId`, or `role` from the request body. Identity comes from the session; ownership comes from the database.

## RBAC vs ABAC

Role-based access control answers "what kind of user are you?" Attribute-based access control answers "does this user satisfy this rule for this object?" Ticketline needs both:

- RBAC for route groups: only organizers and admins can call organizer routes; only gate staff and admins can call scan routes.
- Object checks for scope: an organizer can edit only their own event; gate staff can scan only assigned events.

A pure RBAC model cannot express "my event." A pure ABAC model can become a policy language that nobody can debug. Start with RBAC plus explicit ownership functions. If the rules grow, move them into a small policy module with tests.

## Middleware

Create `apps/api/src/auth/authorize.ts`:

```ts
import type { RequestHandler } from "express";
import type { Role } from "../generated/prisma/index.js";
import { forbidden, unauthorized } from "../errors.js";

export const requireAuth: RequestHandler = (req, _res, next) => {
  if (!req.user) return next(unauthorized());
  next();
};

export function requireRole(...roles: Role[]): RequestHandler {
  return (req, _res, next) => {
    if (!req.user) return next(unauthorized());
    if (!roles.includes(req.user.role)) {
      return next(forbidden("This route requires a different role.", "ROLE_REQUIRED"));
    }
    next();
  };
}
```

`authenticate` attaches the user when a valid session exists. `requireAuth` rejects missing sessions. `requireRole` rejects the wrong role. The middleware does not know about events, so it cannot prove ownership.

## Ownership

Create `apps/api/src/events/access.ts`:

```ts
import type { Event, User } from "../generated/prisma/index.js";
import { forbidden, notFound } from "../errors.js";
import { prisma } from "../db.js";

export function assertEventOwner(user: User, event: Event | null): Event {
  if (!event) throw notFound("Event not found.");
  if (user.role !== "ADMIN" && event.organizerId !== user.id) {
    throw forbidden("You do not own this event.", "NOT_EVENT_OWNER");
  }
  return event;
}

export async function loadOwnedEvent(user: User, eventId: string) {
  const event = await prisma.event.findUnique({ where: { id: eventId } });
  return assertEventOwner(user, event);
}
```

The order matters: load the event, then check ownership, then write. Do not accept `organizerId` from the request body. Do not use a role check as a substitute for the ownership check.

For gate staff, the ownership check is different. A gate staff member can scan an event only if an `EventStaff` row connects them to it. The course adds that table in Week 3. The important part is the shape: load the assignment, then check it, then act.

The assignment is the object. A gate route that checks only `requireRole("GATE_STAFF")` lets any gate staff member scan any event. The fix is not another role; it is a query:

```ts
const assignment = await prisma.eventStaff.findUnique({
  where: { eventId_userId: { eventId, userId: user.id } },
});
if (!assignment) throw forbidden("You are not assigned to this event.", "NOT_EVENT_STAFF");
```

The same pattern applies to a mentor and a course, an organization and its integration, or a buyer and an order. The object changes; the shape does not: load the relationship, then authorize it.

A second worked example makes the difference clear. Gate staff `gs_1` is assigned to `evt_1` but not `evt_2`. They call `POST /scan/events/evt_2` with a valid session and a valid ticket code. The role check passes. The assignment check fails. The response is `403 NOT_EVENT_STAFF`, and no scan row is written. A handler that checks the role and then scans the ticket would admit the attendee to the wrong event.

The assignment check must happen before the ticket lookup or, at minimum, before the scan is recorded. A malicious request should not be able to use the scan endpoint as an oracle for whether a ticket code exists on another event.

## 401, 403, or 404?

- `401` means the request has no valid authentication. The client should sign in.
- `403` means authentication succeeded, but the user may not perform this action.
- `404` means the object does not exist, or you are pretending it does not exist to avoid leaking its existence.

For organizer routes, `403 NOT_EVENT_OWNER` is clear and useful during development. For a private draft, `404` may be safer because it hides whether the event exists. Pick a policy per route and test it. Do not let different handlers choose by accident.

An admin bypass should be explicit and auditable. Put it in `assertEventOwner`, not in ten handlers. Log admin actions with the admin's user ID and the target event.

## A worked example: the other organizer

Database:

```
User org_123  role ORGANIZER
User org_789  role ORGANIZER
Event evt_456 organizerId org_123
```

Organizer `org_789` sends:

```http
PATCH /api/v1/organizer/events/evt_456
{ "title": "Stolen event" }
```

Expected response:

```http
HTTP/1.1 403 Forbidden
{ "success": false, "message": "You do not own this event.", "code": "NOT_EVENT_OWNER" }
```

The event's `updatedAt` must be unchanged. A `403` with a successful write is still a security failure.

What if the event does not exist? Return `404 NOT_FOUND`. What if organizer `org_789` is an admin? Allow the update, but log it. What if the request body contains `organizerId: "org_789"`? Ignore it; the field is not in the update schema.

## How to test authorization

Authorization tests are not an afterthought; they are the proof that the route is safe. A test suite that only logs in as the owner proves the happy path. The valuable tests log in as the wrong actor and assert that nothing changed.

For each route, write four tests:

1. **No session** → `401`.
2. **Wrong role** → `403`.
3. **Right role, wrong object** → `403` or `404`, and the object is unchanged.
4. **Owner** → success.

For list routes, add a fifth: create objects for two owners and assert that the list returns only the caller's objects. For gate routes, assert that unassigned gate staff cannot scan and that assigned staff can. For admin routes, assert the bypass and the audit log.

Use a real database, not a mock. An authorization bug lives in the query and the join, not in the handler's `if`. A mocked Prisma client can make a missing `where` clause pass. The test should create two users and two rows, call the route, and inspect the database.

The test data should be boring and explicit: `owner@example.test`, `other@example.test`, `event_1`, `event_2`. Do not share fixtures between tests; reset the tables. A test that passes because the previous test left the right row in place is worse than no test.

A useful code-review habit is to read every route from the object backward. Start at the write or the sensitive read, find the object it touches, and ask where that object was loaded. If the object came from `req.params`, `req.body`, or a client-provided ID, the ownership check must be visible between the load and the write. If the route uses a helper like `loadOwnedEvent`, verify that the helper actually compares the owner and that every handler uses it. A helper that exists but is skipped in one handler is a false sense of safety.

The same habit catches list routes. A list query should have a `where` clause that includes the caller's identity, not a post-query filter in JavaScript. A post-query filter can leak data through pagination counts, sorting, or an early return. If the query returns 100 rows and the handler filters 99 in memory, the response time and the total count still reveal that the rows exist.

## What can go wrong

**IDOR on every `:id` route.** Event IDs, ticket-type IDs, order IDs, enrollment IDs, and response IDs are all candidates. Test each with two accounts.

**Missing list scoping.** `GET /organizer/events` without `where: { organizerId: user.id }` returns every event. The leak is quieter than a mutation.

**Role from the request body.** A profile update that accepts `role` lets a user promote themselves. Role changes belong in a server-side onboarding endpoint.

**Confused deputy on gate routes.** A gate staff member can scan any event because the handler checks only the role. Load the assignment and check the event ID.

**Admin bypass everywhere.** A single `if (admin) return true` can hide a missing ownership check. Keep the bypass in one function and log it.

**Status code confusion.** Returning `200` with `{ success: false }` makes clients ignore the failure. Use the status code.

**Leaking existence.** Returning "this event belongs to another organizer" tells an attacker the ID is real. Decide whether that matters for the route.

## Build

1. Add `requireAuth` and `requireRole`.
2. Add `assertEventOwner` and `loadOwnedEvent`.
3. Add a protected organizer route stub that uses `loadOwnedEvent`.
4. Add a gate route stub that loads an `EventStaff` assignment (the table arrives in Week 3; use a placeholder check for now).
5. Add the permission matrix to `docs/permissions.md`.
6. Write the ownership unit tests.
7. Add the integration test after the event routes exist in Module 3.

Acceptance criteria:

- No session → `401`.
- Attendee on an organizer route → `403`.
- Organizer on another organizer's event → `403 NOT_EVENT_OWNER`.
- Owner → succeeds.
- Admin → succeeds on any event.
- Changing `organizerId` in the body has no effect.
- The failed request does not change `updatedAt`.

## Verify

Use two organizer accounts and one attendee. For every row in the matrix, send the request and record the status. Then try the direct object attack and inspect the event's `updatedAt`. Finally, add a unit test:

```ts
const organizer = { id: "u1", role: "ORGANIZER" } as const;
const other = { id: "u2", role: "ORGANIZER" } as const;
const admin = { id: "u3", role: "ADMIN" } as const;
const event = { id: "e1", organizerId: "u1" } as never;

expect(assertEventOwner(organizer as never, event)).toBe(event);
expect(() => assertEventOwner(other as never, event)).toThrow();
expect(assertEventOwner(admin as never, event)).toBe(event);
```
