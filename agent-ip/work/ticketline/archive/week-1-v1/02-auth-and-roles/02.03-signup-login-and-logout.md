## The login route that leaks accounts

A login endpoint returns `404 User not found` for an unknown email and `401 Wrong password` for a known email with a bad password. An attacker now has an account-enumeration oracle: they can test email addresses until they find valid accounts, then focus the password attack.

The fix is not a better error message. The fix is to return the same response for both cases and to spend roughly the same time on both paths.

## Validation

Create `apps/api/src/auth/schemas.ts`:

```ts
import { z } from "zod";

export const signupSchema = z.object({
  email: z.string().trim().toLowerCase().email(),
  name: z.string().trim().min(2).max(80),
  password: z.string().min(12).max(200),
});

export const loginSchema = z.object({
  email: z.string().trim().toLowerCase().email(),
  password: z.string().min(1).max(200),
});
```

The password minimum is 12 characters for this course. Do not impose arbitrary character-class rules; length and a breached-password check are stronger. The course discusses breach checks in Week 4.

## Signup

```ts
import { Router } from "express";
import { prisma } from "../db.js";
import { hashPassword } from "../auth/password.js";
import { createSession } from "../auth/create-session.js";
import { setSessionCookie } from "../auth/cookie.js";
import { signupSchema } from "../auth/schemas.js";

export const authRouter = Router();

authRouter.post("/signup", async (req, res, next) => {
  try {
    const input = signupSchema.parse(req.body);

    const existing = await prisma.user.findUnique({ where: { email: input.email } });
    if (existing) {
      return res.status(409).json({
        success: false,
        message: "An account with that email already exists.",
        code: "EMAIL_IN_USE",
      });
    }

    const user = await prisma.user.create({
      data: {
        email: input.email,
        name: input.name,
        passwordHash: await hashPassword(input.password),
      },
    });

    const session = await createSession(user.id);
    setSessionCookie(res, session.token);

    res.status(201).json({
      success: true,
      data: { id: user.id, email: user.email, name: user.name, role: user.role },
    });
  } catch (error) {
    next(error);
  }
});
```

Signup returning `409` does reveal that the email exists. That is a deliberate trade-off: the signup form must tell the user why it failed. Login must not.

## Login

```ts
import { verifyPassword } from "../auth/password.js";
import { loginSchema } from "../auth/schemas.js";

authRouter.post("/login", async (req, res, next) => {
  try {
    const input = loginSchema.parse(req.body);

    const user = await prisma.user.findUnique({ where: { email: input.email } });

    // Always verify something so the timing does not reveal whether the email exists.
    const hash = user?.passwordHash ?? "$argon2id$v=19$m=65536,t=3,p=4$dummy$dummy";
    const valid = await verifyPassword(hash, input.password).catch(() => false);

    if (!user || !valid) {
      return res.status(401).json({
        success: false,
        message: "Invalid email or password.",
        code: "INVALID_CREDENTIALS",
      });
    }

    const session = await createSession(user.id);
    setSessionCookie(res, session.token);

    res.json({
      success: true,
      data: { id: user.id, email: user.email, name: user.name, role: user.role },
    });
  } catch (error) {
    next(error);
  }
});
```

The dummy hash above is illustrative. Use a real precomputed Argon2id hash in your code so the verification cost is comparable. If `verifyPassword` throws on a malformed hash, catch it and treat it as a failed login.

## Logout and me

```ts
import { authenticate } from "../auth/authenticate.js";
import { clearSessionCookie } from "../auth/cookie.js";
import { revokeSession } from "../auth/create-session.js";

authRouter.post("/logout", authenticate, async (req, res) => {
  if (req.sessionId) await revokeSession(req.sessionId);
  clearSessionCookie(res);
  res.status(204).end();
});

authRouter.get("/me", authenticate, (req, res) => {
  if (!req.user) {
    return res.status(401).json({
      success: false,
      message: "Not signed in.",
      code: "AUTH_REQUIRED",
    });
  }

  res.json({
    success: true,
    data: {
      id: req.user.id,
      email: req.user.email,
      name: req.user.name,
      role: req.user.role,
      emailVerified: Boolean(req.user.emailVerifiedAt),
    },
  });
});
```

## Rate limits

Login and signup are credential endpoints; there is no authenticated user yet. Limit by IP and email:

```ts
import rateLimit from "express-rate-limit";

const loginLimiter = rateLimit({
  windowMs: 60_000,
  limit: 10,
  standardHeaders: "draft-7",
  legacyHeaders: false,
  keyGenerator: (req) => `${req.ip}:${String(req.body?.email ?? "")}`,
});
```

Apply a tighter per-email limit and a looser per-IP limit. Do not rely on the client to throttle.

## Verify

```bash
curl -i -X POST http://localhost:4000/api/v1/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"organizer@example.test","name":"Ada","password":"correct horse battery staple"}'

curl -i -X POST http://localhost:4000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"organizer@example.test","password":"wrong-password"}'

curl -i http://localhost:4000/api/v1/auth/me
```

Pass criteria:

- Signup returns `201` and sets `Set-Cookie: tl_session=...; HttpOnly; SameSite=Lax`.
- Wrong password returns `401` with the same body as an unknown email.
- `/me` without a cookie returns `401`.
- `/me` with the cookie returns the user.
- Logout returns `204` and the next `/me` is `401`.

## Key ideas

- Validate and normalise auth input at the API boundary.
- Login failures are generic and timing-comparable.
- Signup can reveal an existing account; login must not.
- Logout revokes the server-side session, not only the cookie.
