## The employee who still has a key

An organizer is removed from the platform at 09:00. Their browser still holds an access token that expires at 09:15. For fifteen minutes, the removed account can still create events. If the same account also holds a refresh token, the window can be much longer.

You can add a denylist, shorten the token lifetime, or rotate keys. Or you can use a session that the server can delete immediately. The choice is not about which token is more modern. It is about which failure you can tolerate.

<ComparePanel title="Opaque sessions versus JWTs">
  <CompareColumn label="Opaque session (this course)">
    The token is a random string.

    The server stores a hash and a row per session.

    Logout and revocation are immediate.

    Every authenticated request reads the session.

    Simple to reason about and test.
  </CompareColumn>
  <CompareColumn label="JWT">
    The token carries signed claims.

    The server can verify it without a lookup.

    Revocation requires a denylist, short expiry, or key rotation.

    Claims can go stale until the token expires.

    Useful for stateless services and cross-domain APIs, but more moving parts here.
  </CompareColumn>
</ComparePanel>

## The Ticketline decision

Ticketline uses **opaque session cookies**:

- The browser receives a random token in an `HttpOnly` cookie.
- The database stores a **hash** of the token, not the token itself.
- The session row contains the user ID and an expiry.
- Logout deletes the row; the next request is unauthenticated.
- A compromised database does not expose usable session tokens.

This is a deliberate trade-off. Every authenticated request does a session lookup. At this scale that is cheap, and the security and revocation properties are worth it.

<BigWordAlert
  term="Opaque token"
  plainEnglish="A random value that carries no user data; the server looks it up to learn who it belongs to."
  whyItMatters="Because the token is random, a stolen database row gives an attacker a hash, not a working session. Because the session is a row, logout can revoke it immediately."

## How the token flows

1. Login verifies the password.
2. The API creates a random token with `crypto.randomBytes(32)`.
3. The API stores `sha256(token)` in `sessions.token_hash`.
4. The API sends the raw token in a cookie.
5. The browser sends the cookie on every same-origin request.
6. The API hashes the cookie value and looks up the session.
7. If the session is missing or expired, the request is unauthenticated.

The raw token never appears in the database, logs, or URL. The hash is enough to find the session and useless if leaked.

## Cookie flags

| Flag | Value | Why |
|---|---|---|
| `HttpOnly` | true | JavaScript cannot read the cookie |
| `Secure` | true in production | The cookie is only sent over HTTPS |
| `SameSite` | `Lax` | Blocks most cross-site POSTs while allowing normal navigation |
| `Path` | `/` | The cookie is sent to the app |
| `Max-Age` | 30 days | The session expires even if the user never logs out |

`SameSite=Lax` is not a complete CSRF defense. In a cross-origin deployment you may need `SameSite=None; Secure` plus a CSRF token. Ticketline uses a same-origin proxy in development, so `Lax` is the right default here. Week 4 revisits the production cookie policy.

## Build: write the decision down

Create `docs/auth-decision.md`:

1. State the choice: opaque sessions.
2. List the two alternatives you considered.
3. State the cost: one session lookup per authenticated request.
4. State the revocation behavior: logout deletes the row.
5. State the cookie policy and the production caveat.

A decision without a cost is marketing. Write the cost.

## Key ideas

- Sessions trade a lookup for immediate revocation and simpler reasoning.
- Store a hash of the token, never the raw token.
- `HttpOnly`, `Secure`, and `SameSite` are part of the auth design.
- Write down the cost of the choice, not only the benefit.
