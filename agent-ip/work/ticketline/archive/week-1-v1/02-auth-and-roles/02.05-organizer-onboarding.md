## Anyone can sign up; not everyone should publish

If signup lets a user choose `role: "ORGANIZER"`, anyone can publish events. If the role is set by a hidden checkbox, the client can change it. The production pattern is an explicit onboarding flow:

1. Signup creates an `ATTENDEE`.
2. The attendee verifies their email.
3. The attendee creates an organizer profile.
4. The API upgrades the role to `ORGANIZER` and records the profile.

The role change is server-side and auditable. The client never sends the role.

## Verification token

Use a random token, store its hash, and make it single-use.

```ts
import { createHash, randomBytes } from "node:crypto";

export function createVerificationToken() {
  return randomBytes(32).toString("base64url");
}

export function hashVerificationToken(token: string) {
  return createHash("sha256").update(token).digest("hex");
}
```

The token TTL should be short: 30 minutes for email verification. Store `expiresAt` and `usedAt`.

## Email delivery with a console fallback

The course must be finishable without an email provider. In development, log the verification link. In production, send it with Resend or another provider.

```ts
import { Resend } from "resend";
import { env } from "../config.js";
import { logger } from "../logger.js";

const resend = env.RESEND_API_KEY ? new Resend(env.RESEND_API_KEY) : null;

export async function sendVerificationEmail(email: string, token: string) {
  const link = `${env.WEB_ORIGIN}/verify-email?token=${token}`;

  if (!resend) {
    logger.info({ email, link }, "verification email (dev fallback)");
    return;
  }

  await resend.emails.send({
    from: env.EMAIL_FROM,
    to: email,
    subject: "Verify your Ticketline email",
    text: `Verify your email: ${link}`,
  });
}
```

Never log the token in production. The dev fallback is explicitly gated by the absence of a provider key and is documented in the README.

## Routes

### Request verification

```ts
authRouter.post("/request-verification", authenticate, requireAuth, async (req, res, next) => {
  try {
    if (req.user!.emailVerifiedAt) {
      return res.status(409).json({
        success: false,
        message: "Email is already verified.",
        code: "ALREADY_VERIFIED",
      });
    }

    const token = createVerificationToken();
    await prisma.emailVerificationToken.create({
      data: {
        userId: req.user!.id,
        tokenHash: hashVerificationToken(token),
        expiresAt: new Date(Date.now() + 30 * 60_000),
      },
    });

    await sendVerificationEmail(req.user!.email, token);
    res.status(202).json({ success: true, data: { sent: true } });
  } catch (error) {
    next(error);
  }
});
```

### Verify email

```ts
authRouter.post("/verify-email", async (req, res, next) => {
  try {
    const { token } = z.object({ token: z.string().min(1) }).parse(req.body);
    const hash = hashVerificationToken(token);

    const record = await prisma.emailVerificationToken.findUnique({ where: { tokenHash: hash } });

    if (!record || record.usedAt || record.expiresAt <= new Date()) {
      return res.status(400).json({
        success: false,
        message: "That verification link is invalid or expired.",
        code: "INVALID_VERIFICATION_TOKEN",
      });
    }

    await prisma.$transaction([
      prisma.user.update({
        where: { id: record.userId },
        data: { emailVerifiedAt: new Date() },
      }),
      prisma.emailVerificationToken.update({
        where: { id: record.id },
        data: { usedAt: new Date() },
      }),
    ]);

    res.json({ success: true, data: { verified: true } });
  } catch (error) {
    next(error);
  }
});
```

### Organizer onboarding

```ts
organizerRouter.post("/onboarding", authenticate, requireAuth, async (req, res, next) => {
  try {
    if (!req.user!.emailVerifiedAt) {
      return res.status(403).json({
        success: false,
        message: "Verify your email before creating an organizer profile.",
        code: "EMAIL_NOT_VERIFIED",
      });
    }

    const input = z.object({
      displayName: z.string().trim().min(2).max(80),
      bio: z.string().trim().max(500).optional(),
      website: z.string().url().optional(),
    }).parse(req.body);

    const profile = await prisma.$transaction(async (tx) => {
      const created = await tx.organizerProfile.create({
        data: { userId: req.user!.id, ...input },
      });
      await tx.user.update({
        where: { id: req.user!.id },
        data: { role: "ORGANIZER" },
      });
      return created;
    });

    res.status(201).json({ success: true, data: profile });
  } catch (error) {
    next(error);
  }
});
```

If the user is already an organizer, return `409` instead of creating a duplicate profile. The `OrganizerProfile.userId` primary key already prevents duplicates; translate the Prisma unique error into a clear response.

## Verify

- Signup → request verification → the dev log prints a link.
- The link marks the email verified and cannot be used twice.
- Onboarding before verification returns `403 EMAIL_NOT_VERIFIED`.
- Onboarding after verification creates a profile and changes the role to `ORGANIZER`.
- A second onboarding request does not create a duplicate profile.
- The client cannot set `role` in any request body.

## Key ideas

- Signup creates an attendee; organizer status is earned through an explicit flow.
- Verification tokens are random, hashed, single-use, and short-lived.
- Email has a console fallback so the course works offline.
- Role changes happen server-side in a transaction.
