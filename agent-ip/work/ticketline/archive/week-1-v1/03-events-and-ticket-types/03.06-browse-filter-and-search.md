## The catalogue that showed drafts

A public catalogue query returns every event ordered by date. It works in development because there are two events. In production, it leaks drafts, cancelled events, and events from organizers who never finished setup.

The fix is not a filter in the UI. The public query must start from the public state: `status = PUBLISHED`, ordered by `startsAt`, with a page limit.

## Query contract

Create a shared schema:

```ts
import { z } from "zod";

export const eventListQuerySchema = z.object({
  q: z.string().trim().max(100).optional(),
  from: z.coerce.date().optional(),
  to: z.coerce.date().optional(),
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(50).default(12),
});
```

The limit is capped so a client cannot ask for 10,000 rows. The page is 1-indexed.

## Public list route

```ts
publicEventRouter.get("/events", async (req, res, next) => {
  try {
    const query = eventListQuerySchema.parse(req.query);
    const skip = (query.page - 1) * query.limit;

    const where = {
      status: "PUBLISHED" as const,
      ...(query.from || query.to
        ? {
            startsAt: {
              ...(query.from ? { gte: query.from } : {}),
              ...(query.to ? { lte: query.to } : {}),
            },
          }
        : {}),
      ...(query.q
        ? {
            OR: [
              { title: { contains: query.q, mode: "insensitive" as const } },
              { venueName: { contains: query.q, mode: "insensitive" as const } },
            ],
          }
        : {}),
    };

    const [items, total] = await prisma.$transaction([
      prisma.event.findMany({
        where,
        orderBy: { startsAt: "asc" },
        skip,
        take: query.limit,
        select: {
          id: true,
          slug: true,
          title: true,
          venueName: true,
          timezone: true,
          startsAt: true,
          coverImageKey: true,
        },
      }),
      prisma.event.count({ where }),
    ]);

    res.json({
      success: true,
      data: {
        items,
        page: query.page,
        limit: query.limit,
        total,
        totalPages: Math.ceil(total / query.limit),
      },
    });
  } catch (error) {
    next(error);
  }
});
```

The `select` is deliberate. The catalogue does not need the full description or ticket types. Return only the card fields.

## Index reality

`@@index([status, startsAt])` helps the published-and-date filter. A `contains` search with a leading wildcard (`%ticket%`) does not use a normal B-tree index. At the course's scale, that is fine. At real scale, use one of:

- PostgreSQL full-text search (`tsvector`, `GIN`);
- trigram indexes (`pg_trgm`);
- an external search service.

Do not claim the contains query is indexed when it is not. Write the limit down in `docs/decisions.md` and revisit it if the catalogue grows.

## Web catalogue

The web page should:

- fetch the public list with the current query;
- render a search input and date filters;
- show an empty state when nothing matches;
- show pagination or a "load more" control;
- keep the URL in sync with the query so the result is shareable;
- use the event's time zone for the card date.

A simple server component can read `searchParams` and call the API. Keep the first version server-rendered; add client-side interactivity only if the UX needs it.

## Verify

- A draft event never appears in the public list.
- `?q=live` matches title or venue, case-insensitively.
- `?from=...&to=...` filters by `startsAt`.
- `?limit=1000` is rejected or capped at 50.
- Page 2 returns the next slice and the same total.
- An empty result shows a helpful empty state, not a blank page.
