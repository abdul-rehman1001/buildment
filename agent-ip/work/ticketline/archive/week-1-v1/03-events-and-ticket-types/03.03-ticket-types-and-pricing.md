## The price that changed after purchase

An organizer sells 40 early-bird tickets at $45. A week later they raise the price to $60. A buyer opens an old order and sees $60. The buyer paid $45; the receipt now says $60. Support has to reconcile the difference manually.

The fix is not to freeze the ticket type forever. The fix is to snapshot the price at the moment the buyer commits: on the hold, and again on the order. The ticket type can change; the order must not.

<BigWordAlert
  term="Price snapshot"
  plainEnglish="The price recorded at the moment of purchase, copied onto the order so later price changes do not rewrite history."
  whyItMatters="Ticket types are mutable. Orders are evidence. The order stores what the buyer actually agreed to pay."

## The ticket type contract

Create `packages/shared/src/ticket-type.ts`:

```ts
import { z } from "zod";

export const ticketTypeInputSchema = z
  .object({
    name: z.string().trim().min(2).max(60),
    description: z.string().trim().max(500).optional(),
    priceCents: z.number().int().min(0).max(1_000_000),
    capacity: z.number().int().min(1).max(100_000),
    maxPerOrder: z.number().int().min(1).max(20),
    salesStartAt: z.coerce.date(),
    salesEndAt: z.coerce.date(),
  })
  .refine((value) => value.maxPerOrder <= value.capacity, {
    message: "The per-order limit cannot exceed capacity.",
    path: ["maxPerOrder"],
  })
  .refine((value) => value.salesEndAt > value.salesStartAt, {
    message: "The ticket sale window is invalid.",
    path: ["salesEndAt"],
  });

export type TicketTypeInput = z.infer<typeof ticketTypeInputSchema>;
```

The price is an integer. The currency is stored separately, defaulting to `USD` for the course. Do not accept a float from JSON and round it silently.

## Create a ticket type

```ts
organizerEventRouter.post("/events/:id/ticket-types", async (req, res, next) => {
  try {
    const event = await loadOwnedEvent(req.user!, req.params.id);
    const input = ticketTypeInputSchema.parse(req.body);

    if (input.salesStartAt < event.salesStartAt || input.salesEndAt > event.salesEndAt) {
      return res.status(400).json({
        success: false,
        message: "The ticket sale window must fit inside the event sale window.",
        code: "INVALID_SALE_WINDOW",
      });
    }

    const ticketType = await prisma.ticketType.create({
      data: {
        ...input,
        eventId: event.id,
      },
    });

    res.status(201).json({ success: true, data: ticketType });
  } catch (error) {
    next(error);
  }
});
```

The unique constraint on `(eventId, name)` is the final guard against duplicate tiers. Translate Prisma `P2002` into `409 TICKET_TYPE_EXISTS` in the error handler.

## Update a ticket type

```ts
organizerEventRouter.patch(
  "/events/:id/ticket-types/:ticketTypeId",
  async (req, res, next) => {
    try {
      const event = await loadOwnedEvent(req.user!, req.params.id);
      const input = ticketTypeInputSchema.partial().parse(req.body);

      const ticketType = await prisma.ticketType.findFirst({
        where: { id: req.params.ticketTypeId, eventId: event.id },
      });

      if (!ticketType) {
        return res.status(404).json({
          success: false,
          message: "Ticket type not found.",
          code: "NOT_FOUND",
        });
      }

      const updated = await prisma.ticketType.update({
        where: { id: ticketType.id },
        data: input,
      });

      res.json({ success: true, data: updated });
    } catch (error) {
      next(error);
    }
  }
);
```

The `findFirst` includes `eventId` in the `where` clause. That is an object-level check inside the query, not a role check.

## Publish readiness

Revisit the publish guard from 3.1. It must reject an event with no ticket types or a zero-capacity tier. Add ticket-type checks to `assertEventReady`:

```ts
if (event.ticketTypes.length === 0) problems.push("Add at least one ticket type.");
if (event.ticketTypes.some((t) => t.capacity <= 0)) problems.push("Every ticket type needs capacity.");
if (event.ticketTypes.some((t) => t.salesEndAt <= t.salesStartAt)) problems.push("A ticket sale window is invalid.");
```

Do not let an organizer publish a shell with no way to buy.

## The snapshot decision

In Week 1, no order exists yet. In Module 4, a hold will store `priceCents` at creation. In Module 5, the order will store `priceCents`, `currency`, and the ticket-type name. The ticket type remains mutable for future sales; the order remains evidence of the past.

Write this down in `docs/decisions.md`:

> Ticket types are mutable. Holds and orders snapshot the price at the moment of commitment. A later price change never rewrites an existing order.

## Verify

- A price of `-1` returns `400`.
- A capacity of `0` returns `400`.
- `maxPerOrder > capacity` returns `400`.
- A sale window outside the event window returns `400`.
- Two tiers with the same name on one event return `409`.
- An event with no tiers fails to publish with `422`.
- The public event response shows the tier price as cents and a formatted display value.

## Key ideas

- Prices are integer cents; capacity and per-order limits are validated.
- The ticket sale window must fit inside the event sale window.
- Ticket types are mutable; holds and orders snapshot the price.
- Publish readiness includes at least one valid ticket type.
