## The course that tried to build everything

A common first version of a ticketing project includes seat maps, transfers, refunds, discount codes, a mobile app, a recommendation feed, and a waiting room. Six weeks later, the checkout still double-books the last ticket because the team spent its time on the seat map.

Ticketline takes the opposite approach. The core is one loop:

> **Publish an event → hold inventory → pay → issue a ticket → scan it once.**

Every feature is judged by whether it makes that loop more trustworthy. If it does not, it is stretch or out of scope.

## The scope ladder

| Layer | What is in it | Why |
|---|---|---|
| **Core** | Auth and roles, events and ticket types, capacity, holds, Stripe test checkout, webhooks, QR tickets, check-in, tests, deploy | These are the product and the production lessons |
| **Should have** | Refunds, search and filters, email delivery, organizer dashboard, minimal admin | They make the product usable and the demo credible |
| **Stretch** | Seat maps, Elements checkout, transfers, waiting room, PDF tickets, load test | They add depth without blocking the core |
| **Out of scope** | Real payments, payouts, PCI, dynamic pricing, resale, native apps, full offline-first sync, multi-currency, tax | They add cost or risk without teaching the core |

The boundary is not a suggestion. If you spend a day on a stretch feature while the core race test fails, you have made the course harder, not better.

## The four-week shape

| Week | Focus | What must work by the end |
|---|---|---|
| 1 | Foundation and organizer flow | Organizer publishes an event; buyer finds it |
| 2 | Inventory and payments | Last-ticket race is safe; paid order issues tickets |
| 3 | Tickets and gate | QR ticket scans once; offline sync works |
| 4 | Hardening and defense | Deployed system, passing tests, runbook, viva |

Each week ends with a demo, not a status update. If the demo does not work, the week is not done.

## The cut rule

When you are behind, cut in this order:

1. **Polish** — animations, empty-state illustrations, extra dashboard charts.
2. **Stretch features** — seat maps, transfers, PDFs.
3. **Should-have features** — search filters, admin console.
4. **Never cut** — the four invariants, the race test, duplicate-webhook handling, duplicate-scan handling, the deployed demo.

Cutting a feature is a decision, not a failure. Cutting the invariant test is a different project.

## Common questions

<FaqGroup title="Scope questions">
  <FaqItem question="Can I use MongoDB instead of PostgreSQL?">
    Not for this course. The core lesson is a relational invariant under concurrency: conditional updates, row locks, and transactions. MongoDB can model this, but the course's tests and schema are written for PostgreSQL. Use the stack the course can validate.
  </FaqItem>
  <FaqItem question="Can I add a seat map in Week 1?">
    No. The core uses general-admission ticket types with capacity. Seat maps are a Sports/Cinema variant feature. Build the hold and race test first.
  </FaqItem>
  <FaqItem question="Do I need a real Stripe account?">
    A Stripe test-mode account is enough. No real money moves. If you cannot create one yet, complete the inventory and ticket weeks first and return to payments with the test keys.
  </FaqItem>
  <FaqItem question="Can I skip tests to finish faster?">
    No. The race test, duplicate-webhook test, and duplicate-scan test are the evidence that the product works. Skipping them means you have a demo, not a capstone.
  </FaqItem>
  <FaqItem question="What if I fall behind?">
    Cut in the order above. Keep the core loop, the invariant tests, and the deployed demo. Add stretch work only after the demo is honest.
  </FaqItem>
</FaqGroup>

## Build: write the scope document

Create `docs/scope.md` in your project with four sections:

1. **Core acceptance criteria** — the smallest demo you will ship.
2. **Should-have** — features you will add if the core is green.
3. **Stretch** — features you will only attempt after the core.
4. **Non-goals** — what you will explicitly not build, and why.

Write the non-goals in your own words. "No real payments because the course uses Stripe test mode and no money should move" is a better non-goal than "payments later".

## Key ideas

- The core loop is publish → hold → pay → issue → scan.
- The scope ladder separates core, should-have, stretch, and non-goals.
- Cut polish and stretch first; never cut the invariant tests or the deployed demo.
- A non-goal is a decision, not an apology.
