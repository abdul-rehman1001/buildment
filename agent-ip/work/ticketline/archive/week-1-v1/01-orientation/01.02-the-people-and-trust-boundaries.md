## The event ID in the URL

An organizer opens their dashboard and edits event `evt_123`. The request looks like this:

```
PATCH /api/v1/organizer/events/evt_123
```

A curious attendee changes `evt_123` to `evt_456` and sends the same request with their own valid session cookie. The API sees a signed-in user and a valid route. If the handler updates `evt_456` without checking who owns it, the attendee has just edited someone else's event.

The user was authenticated. The route was authorized by role. The object was not authorized. This is the most common authorization bug in multi-tenant products, and it is the reason this chapter exists before any feature code.

<BigWordAlert
  term="IDOR"
  plainEnglish="Insecure Direct Object Reference — trusting an ID from the client without checking that the signed-in user is allowed to access that object."
  whyItMatters="Every organizer route that takes an event ID must load the event and compare its organizerId with the session user."
/>

## The four actors

| Actor | Can | Cannot |
|---|---|---|
| **Attendee** | Browse published events, create holds, pay, view their own tickets and orders | Create or edit events, scan tickets, see another buyer's order |
| **Organizer** | Create and edit their own events, define ticket types, publish, view their sales, refund their orders | Edit another organizer's event, see platform-wide data |
| **Gate staff** | Scan tickets for assigned events, view scan results, work offline | Edit events, issue refunds, see payment details |
| **Admin** | View users and events, intervene in support cases, grant roles | Impersonate users, read raw card data |

Roles are global for this course, but permissions are scoped. An organizer is not "allowed to edit events" in general. They are allowed to edit *their* events. A gate staff member is not "allowed to scan tickets" in general. They are allowed to scan *assigned* events.

## The trust boundaries

<ArchitectureDiagram title="Ticketline trust boundaries">
  <ArchNode layer="Client">Browser · Next.js pages · scanner UI</ArchNode>
  <ArchNode layer="API">Express · session auth · validation · authorization · business rules</ArchNode>
  <ArchNode layer="Data">PostgreSQL · Redis · object storage</ArchNode>
  <ArchNode layer="External">Stripe · email provider</ArchNode>
</ArchitectureDiagram>

- **The browser is untrusted.** It can send any event ID, any price, any role, and any ticket code. The API validates every field and derives identity from the session, never from the request body.
- **The API is the trust boundary.** It owns authorization, price calculation, inventory, and ticket issuance. If a rule matters, it lives here.
- **The database is the last line of defense.** Constraints and transactions enforce invariants even when two API requests race.
- **External services are not authoritative for your business rules.** Stripe tells you a payment succeeded; it does not tell you whether the buyer owns the hold. Your API decides.

## Role checks versus object checks

A role check answers "what kind of user are you?" An object check answers "may this user touch this specific row?"

<ComparePanel title="Two authorization questions">
  <CompareColumn label="Role check">
    `requireRole("ORGANIZER")`

    Proves the user is an organizer.

    It does **not** prove the user owns event `evt_456`.
  </CompareColumn>
  <CompareColumn label="Object check">
    `assertEventOwner(user.id, event.organizerId)`

    Proves this organizer owns this event.

    It runs after the event is loaded and before any write.
  </CompareColumn>
</ComparePanel>

The production pattern is both: authenticate, authorize the role, load the object, authorize the object. The order matters. A role check that runs before the object load is necessary but not sufficient.

## Build: write the permission matrix

Before you write a route, write the matrix. Create `docs/permissions.md` in your project and fill it in for the Week 1 endpoints:

| Endpoint | Attendee | Organizer (owner) | Organizer (other) | Gate staff | Admin |
|---|---|---|---|---|---|
| `GET /events` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `POST /organizer/events` | — | ✓ | — | — | ✓ |
| `PATCH /organizer/events/:id` | — | ✓ | — | — | ✓ |
| `POST /organizer/events/:id/publish` | — | ✓ | — | — | ✓ |
| `GET /organizer/events` | — | own only | — | — | all |

Then add one column for the object check: "owner only" or "assigned event only". If a route does not have an object check, write down why.

## Key ideas

- Authentication, role authorization, and object authorization are three different checks.
- The browser is untrusted; identity comes from the session, not the request body.
- Every organizer route that takes an event ID needs an ownership check.
- The database is the last line of defense for invariants.
