## The secret in the browser

A developer builds a checkout page and puts the Stripe secret key in a `NEXT_PUBLIC_` environment variable. The page works. Then someone opens the browser bundle and reads the key. The secret is now public, and the test account is compromised.

The mistake is architectural, not a typo. Secrets belong to the server. The browser gets a public key and a session cookie; it never gets a database URL, a Stripe secret, or an S3 secret.

<BigWordAlert
  term="Trust boundary"
  plainEnglish="A line between two parts of the system where the level of trust changes."
  whyItMatters="The browser is untrusted. Every rule that matters — price, ownership, capacity, ticket validity — must be enforced on the API side of that line."
/>

## The topology

<ArchitectureDiagram title="Ticketline request path">
  <ArchNode layer="Client">Browser · Next.js pages · scanner UI</ArchNode>
  <ArchNode layer="API">Express · auth · events · holds · checkout · scan</ArchNode>
  <ArchNode layer="Data">PostgreSQL · Redis · S3-compatible storage</ArchNode>
  <ArchNode layer="External">Stripe · email provider</ArchNode>
</ArchitectureDiagram>

- **Web (Next.js):** renders the catalogue, organizer dashboard, checkout, and scanner. It calls the API over HTTP. It may cache public reads, but it never owns a business rule.
- **API (Express):** validates input, authenticates the session, enforces authorization, owns inventory and pricing, talks to Stripe, and writes the database.
- **PostgreSQL:** the source of truth for users, events, ticket types, holds, orders, tickets, and scans. Constraints and transactions protect the invariants.
- **Redis:** delayed jobs and short-lived coordination. It is not the source of truth for inventory.
- **Object storage:** event cover images. The database stores the object key, not the image bytes.
- **Stripe:** payment processing in test mode. The API creates the payment and verifies the webhook; the browser never sees the secret.
- **Email:** ticket delivery and verification. In development, the API logs the link instead of sending it.

## Why split the web and the API?

A single Next.js app with server actions is a valid architecture. This course splits them for three reasons:

1. **The trust boundary becomes visible.** The learner writes the API authorization and sees the browser cannot enforce it.
2. **The deployment boundary becomes real.** Web and API can scale and deploy independently.
3. **The tests become cheaper.** The API is a plain Express app; supertest exercises it without a browser.

The cost is setup time. The monorepo and shared package below are designed to keep that cost small.

## Environment variables

Create `.env.example` at the repository root. Do not commit `.env`.

```
DATABASE_URL=postgresql://ticketline:ticketline@localhost:5432/ticketline
SESSION_SECRET=replace-me-with-32-random-bytes
PORT=4000
WEB_ORIGIN=http://localhost:3000
API_ORIGIN=http://localhost:4000
REDIS_URL=redis://localhost:6379
S3_ENDPOINT=http://localhost:9000
S3_REGION=us-east-1
S3_ACCESS_KEY=minio
S3_SECRET_KEY=minio-secret
S3_BUCKET=ticketline
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
RESEND_API_KEY=
EMAIL_FROM=Ticketline <tickets@example.test>
```

The API reads this file with a validated config module in 1.6. The web app only needs `API_URL` for its server-side proxy.

## Build: scaffold the workspace

Create the root and the workspace file:

<TerminalBlock title="Create the monorepo" cwd="~/projects">
  <TerminalLine type="prompt" content="mkdir ticketline && cd ticketline" />
  <TerminalLine type="prompt" content="pnpm init" />
  <TerminalLine type="prompt" content="mkdir -p apps packages/shared/src" />
</TerminalBlock>

`pnpm-workspace.yaml`:

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

Root `package.json` scripts:

```json
{
  "name": "ticketline",
  "private": true,
  "packageManager": "pnpm@10",
  "scripts": {
    "dev": "pnpm -r --parallel dev",
    "build": "pnpm -r build",
    "typecheck": "pnpm -r typecheck",
    "lint": "pnpm -r lint",
    "test": "pnpm -r test",
    "db:migrate": "pnpm --filter api prisma migrate dev"
  }
}
```

Create the web app and the API:

<TerminalBlock title="Create the apps" cwd="ticketline">
  <TerminalLine type="prompt" content="pnpm create next-app@latest apps/web --typescript --tailwind --eslint --app --src-dir --import-alias '@/*' --use-pnpm" />
  <TerminalLine type="prompt" content="mkdir -p apps/api/src apps/api/prisma" />
  <TerminalLine type="prompt" content="cd apps/api && pnpm init && pnpm add express@5 cors cookie-parser helmet pino pino-http zod @prisma/client && pnpm add -D typescript tsx prisma @types/express @types/cors @types/cookie-parser @types/node vitest supertest @types/supertest" />
</TerminalBlock>

`apps/api/package.json` must include `"type": "module"` and scripts:

```json
{
  "type": "module",
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc -p tsconfig.json",
    "typecheck": "tsc --noEmit",
    "lint": "eslint src",
    "test": "vitest run",
    "prisma": "prisma"
  }
}
```

Add `docker-compose.yml` at the root:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ticketline
      POSTGRES_PASSWORD: ticketline
      POSTGRES_DB: ticketline
    ports: ["5432:5432"]
    volumes: ["ticketline-pg:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ticketline -d ticketline"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: minio
      MINIO_ROOT_PASSWORD: minio-secret
    ports: ["9000:9000", "9001:9001"]
    volumes: ["ticketline-minio:/data"]

volumes:
  ticketline-pg:
  ticketline-minio:
```

Start the services and confirm they are healthy:

<TerminalBlock title="Start local services" cwd="ticketline">
  <TerminalLine type="prompt" content="docker compose up -d" />
  <TerminalLine type="output" content="Container ticketline-postgres-1  Healthy" />
  <TerminalLine type="output" content="Container ticketline-redis-1     Started" />
  <TerminalLine type="output" content="Container ticketline-minio-1     Started" />
</TerminalBlock>

## Verify

- `pnpm install` completes from the repository root.
- `docker compose ps` shows Postgres, Redis, and MinIO running.
- `pnpm --filter web dev` starts Next.js on `:3000`.
- `pnpm --filter api dev` starts the API on `:4000` (the health route arrives in 1.6).
- No secret is present in a `NEXT_PUBLIC_` variable.

## Key ideas

- The browser is outside the trust boundary; secrets and business rules live on the server.
- The API owns auth, authorization, inventory, pricing, and ticket issuance.
- PostgreSQL is the source of truth; Redis and storage are supporting services.
- The monorepo keeps the shared contract and CI simple.
