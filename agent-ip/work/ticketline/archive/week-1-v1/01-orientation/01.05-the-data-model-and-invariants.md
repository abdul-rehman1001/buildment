## The table that should not exist

A common first schema stores `available_tickets` on the event and decrements it from the API:

```ts
await db.event.update({
  where: { id: eventId },
  data: { availableTickets: { decrement: quantity } }
});
```

It looks correct until two requests run at the same time. Both read 1, both decrement, and the column reaches -1. The bug is not the `decrement`; the bug is that the invariant is represented as a mutable number with no guard.

The schema must make the invariant explicit: capacity is fixed, sold and held are tracked separately, and a constraint or conditional update ensures they never exceed capacity.

## Week 1 tables

| Table | Purpose | Invariant |
|---|---|---|
| `users` | Identity, role, verification | Email is unique; role is one of four values |
| `sessions` | Opaque session tokens | Token hash is unique; expired sessions are rejected |
| `email_verification_tokens` | Single-use email verification | Token hash is unique; a token is used once |
| `events` | Organizer-owned events | Slug is unique; only an owner can edit |
| `ticket_types` | Priced capacity for an event | `sold_quantity + held_quantity <= capacity` |

Later weeks add `holds`, `orders`, `tickets`, `scans`, and `event_staff`.

## Three modelling decisions

### 1. Money is an integer number of cents

Use `priceCents Int`, not a floating-point dollar amount. `19.99` is not exactly representable in binary floating point; a cent lost or gained in a price calculation is a support ticket. Format at the edge, store an integer.

### 2. Instants are UTC; display uses the event zone

Store `startsAt`, `endsAt`, and sale windows as `DateTime` in UTC. Store the event's IANA zone (`America/New_York`, `Europe/London`) for display and validation. A timestamp without a zone is a bug waiting for a daylight-saving transition.

### 3. Status is an enum

`DRAFT`, `PUBLISHED`, `CANCELLED`, `COMPLETED` are a closed set. An enum in PostgreSQL prevents a typo from creating an unreachable state. The transition rules still live in the API; the enum only guarantees the vocabulary.

## The Prisma schema

Create `apps/api/prisma/schema.prisma` with this Week 1 model. Keep the generator output path consistent with the rest of the course.

```prisma
generator client {
  provider = "prisma-client-js"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

enum Role {
  ATTENDEE
  ORGANIZER
  GATE_STAFF
  ADMIN
}

enum EventStatus {
  DRAFT
  PUBLISHED
  CANCELLED
  COMPLETED
}

model User {
  id                String   @id @default(cuid())
  email             String   @unique
  name              String
  passwordHash      String
  role              Role     @default(ATTENDEE)
  emailVerifiedAt   DateTime?
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  sessions          Session[]
  verificationTokens EmailVerificationToken[]
  events            Event[]

  @@index([role])
}

model Session {
  id        String   @id @default(cuid())
  tokenHash String   @unique
  userId    String
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
}

model EmailVerificationToken {
  id        String    @id @default(cuid())
  tokenHash String    @unique
  userId    String
  expiresAt DateTime
  usedAt    DateTime?
  createdAt DateTime  @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}

model Event {
  id            String      @id @default(cuid())
  organizerId   String
  slug          String      @unique
  title         String
  description   String
  venueName     String
  venueAddress  String
  timezone      String
  startsAt      DateTime
  endsAt        DateTime
  salesStartAt  DateTime
  salesEndAt    DateTime
  status        EventStatus @default(DRAFT)
  coverImageKey String?
  createdAt     DateTime    @default(now())
  updatedAt     DateTime    @updatedAt

  organizer   User         @relation(fields: [organizerId], references: [id], onDelete: Cascade)
  ticketTypes TicketType[]

  @@index([organizerId])
  @@index([status, startsAt])
}

model TicketType {
  id            String   @id @default(cuid())
  eventId       String
  name          String
  description   String?
  priceCents    Int
  currency      String   @default("USD")
  capacity      Int
  soldQuantity  Int      @default(0)
  heldQuantity  Int      @default(0)
  maxPerOrder   Int      @default(4)
  salesStartAt  DateTime
  salesEndAt    DateTime
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  event Event @relation(fields: [eventId], references: [id], onDelete: Cascade)

  @@unique([eventId, name])
  @@index([eventId])
}
```

The counter columns are denormalised on purpose: the public page should not aggregate every order on every read. The write path that keeps them correct arrives in Module 4. Until then, they stay at zero, and the public page shows capacity.

## Prisma 7 config

Prisma 7 expects the connection URL in `prisma.config.ts`, not in `schema.prisma`:

```ts
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations" },
  datasource: { url: process.env.DATABASE_URL! },
});
```

- Five tables exist: `users`, `sessions`, `email_verification_tokens`, `events`, `ticket_types`.

```openquestion
minWords: 100
modelAnswer: "The ticket_types table owns capacity, sold_quantity, and held_quantity. Module 4 will enforce the invariant with a conditional update or a row lock inside a transaction, so only one claim can move the counters while they remain within capacity. A plain decrement of a single available_tickets column has no guard: two concurrent requests can both read enough availability and both decrement, producing a negative count. The invariant needs a compare-and-set or lock, not a blind arithmetic update."
```

## Key ideas

- The schema is the last line of defense for invariants.
- Store money in cents and instants in UTC; store the event zone for display.
- Counters are a read optimisation; the write path must keep them correct.
- Unique constraints and indexes are part of the design, not an afterthought.
